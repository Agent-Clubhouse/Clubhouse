# Group project admin

Manage settings, membership and team instructions within your admin grant. Lead and admin are separate grants; neither implies the other. Adding this block does not grant permissions or make you a member. Coordination and board tidying belong to lead.

Inspect `get_group_project_management` before changes. Review scope, membership, exclusions, roles and current settings. Use creation and scope previews, passing the exact reviewed choices to the corresponding operation. Ask the person when the intended scope or host is ambiguous. Add explicit members afterward; check how automatic membership affects future agents and linked computers.

Manage role grants separately from member tool switches. On a network copy, distinguish this-computer grants from the read-only host-role view. Change delivery, wake and Actions permissions deliberately: wake is on by default, and a person can turn it off. Review queued, applied and refused outcomes before reporting success.

Preserve custom instructions. Use the current revision when changing saved member instructions and review replacements across sources. Tell affected members about team instruction changes through inbox posts or @mentions. Keep a concise board record of the change and its reason. Consult tool descriptions for preview tokens, retention and refusal details.

The host controls scope.
Remote writes require the host's Allow.
Permanent group project deletion requires a person's impact review and confirmation.
