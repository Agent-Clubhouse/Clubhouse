# Annex Network

Epic: #3056. Stages land in order: #3057 (peer basics), #3058 (reachability), #3060 (network channel), then #3061 onward.

## Model

- **A device** is anything paired with this machine, phone or computer, keyed by its identity fingerprint. `annex-peers.json` holds one entry per device with its pinned certificate and its role (it controls this machine, or this machine controls it).
- **The device list** (`src/main/services/annex-devices.ts`) is every paired device with where it stands: `connected`, `connecting`, `offline` or `needs-pairing`, and a problem when one is known. Settings is built from it. IPC: `annex:list-devices`, `annex:remove-device`, `annex:devices-changed`.
- **Reaching a satellite** (`src/main/services/annex-reach.ts`): each satellite entry remembers where it was reached (`knownHosts`, newest first, plus the hosts in its pairing link), with TLS ports per address (`hostPorts`, keyed by lowercase host), and can hold a host the person typed (`typedHost`), such as a tailnet name. `mainPort` remains the legacy default. Old records seed each host's port from that default without removing peers or fields; bare hosts and `mainPort` stay readable by older builds. The pinned certificate decides whether an endpoint really reaches the satellite.
- **The network channel** (`src/main/services/annex-network-channel.ts`, protocol in `src/shared/annex-network-protocol.ts`): a WebSocket at `/network` on the main TLS port that carries membership only (`hello`, `members`, `member-joined`, `member-removed`, `member-renamed`). Anything else closes it with 4400.
- **Membership** (`src/main/services/annex-network-membership.ts`): a member is a peer with role `member`, which both controls and is controlled. `annex-network.json` keeps removals (so members that were off learn of them) and which members have confirmed each join and removal.
- **Phones** (#3062): a phone that pairs with `network: 1` is a member of kind `phone`. The contract for the iOS app is `docs/annex-network-phone.md`.
- **Agent addresses** (`src/shared/agent-address.ts`, #3063): `<agentId>@<machine fingerprint>`; a bare id means this machine. Converts to and from the renderer's `remote||<machine>||<agentId>`.
- **Chat across desktops** (#2390): a controller reads and drives a satellite's chat agents through the same pinned routes and commands phones use (`docs/mobile-control-v1.md`). In the renderer, `stores/remoteChatBackend.ts` is the chat store's backend for namespaced (`remote||…`) agents.
- **Agents across machines** (`src/main/services/annex-agent-calls.ts`, #3064): a connection to an agent on another machine is a binding whose target is its address. Its tool calls go to that machine (`POST /api/v1/network/agent-call`), which checks them against its own connection store (D129) and runs them with the same tool code. Each direction that involves another machine is kept on both machines and sent on every connect (`POST /api/v1/network/connections`). The Connections card lists them under "On other computers" and connects to an agent on a connected computer.
- **A problem** (`src/shared/annex-problems.ts`) is a classified reason a connection failed, shown as two sentences: what happened, and what to do.

## Handoff lifecycle foundation

The internal handoff record (`src/shared/handoffs.ts`, #3338) is separate from the existing orchestrator `hand_off` tool. This foundation does **not** register agent tools, enable transfers, apply files, or wake agents.

An immutable, bounded offer names machine-qualified sender and receiver addresses, or a receiving machine's Dispatcher. The receiving machine serializes acceptance, decline, sender cancellation and subsequent progress. A Dispatcher must explicitly select an agent on its own machine. Acceptance alone never starts a transfer in this slice.

The state sequence is `offered` -> `accepted` -> `transferring` -> `verifying` -> `applying` -> `applied`. Decline ends an offer; failure ends any active state. Only the sender can cancel, and only before `applying`. A remote cancellation is a command to the receiving authority, not a local rollback. Command versions prevent competing decisions; stable operation UUIDs reconcile responses and cancellations whose acknowledgements were lost.

`handoffs.json` in app user data stores complete append-only histories with atomic, owner-only writes. A successful response means its record was persisted; reads never expose an uncommitted write. Corrupt or unsupported files block reads and writes without replacing the original. The store holds at most 1,000 records, each with a 256-character title, 16,000-character brief and 256 history entries (the last entry is reserved for a terminal state). Actual UTF-8 encoded JSON is capped at 384 KiB, leaving headroom below the 512 KiB transport envelope; nonterminal records reserve 64 KiB for a terminal event and its derived result, including worst-case JSON escaping. Oversized records are refused, never truncated.

Lifecycle records and their history are app-owned operational state, not a person's settings. The settings audit inventory explicitly classifies `handoffs.json` as not settings, like Actions and their run history; lifecycle writes do not emit fake settings-change audit entries.

Receiver snapshots must preserve the immutable offer and history prefix. They are accepted only from the authenticated receiving machine; offers only from the authenticated sender. Transport registration and durable command delivery remain separate integration work.

Before entering `applying`, a worker must persist the registered project id, reserved worktree/branch and staging UUID. Restart during `applying` records `failed` with `recovery/indeterminate_apply`, retaining that checkpoint. This does not claim rollback or absence of filesystem side effects, and never retries automatically. Earlier transfer states remain resumable, but worker transitions recheck both parties' grants and connection authorization.

### Transfer safety foundation (not enabled)

`handoff-manifest.ts` defines a canonical, SHA-256-ready worktree manifest with regular files, executable modes and explicit deletions. It rejects traversal, `.git` internals and aliases, symlink modes, Windows device/alternate-stream names, case/Unicode collisions, conflicting paths, invalid hashes, unsafe remote URLs and inconsistent byte totals. Ill-formed UTF-16 is rejected before encoding; paths and selection patterns containing Unicode default-ignorable characters are refused, not rewritten, to avoid HFS aliases of `.git` and other names. Complete manifests are capped at 2 MiB. Default bounds are 1 GiB total, 256 MiB per file and 10,000 file/deletion entries; the internal configurable ceiling cannot exceed 16 GiB. Configuration UI and byte transport are not wired.

`handoff-secrets.ts` contains fixed, case-insensitive sensitive-path rules and high-confidence credential-content rules. Findings contain only a redacted path, rule id and optional line number, never a matched value. Known credentials embedded in filenames are also blocked and redacted. UTF-8 text up to 1 MiB is scanned by content; binary and larger files receive name checks only. Auth configuration that cannot be inspected is blocked. `.env.example`, `.env.sample` and `.env.template` are exempt by name, not by content. Handoff records, including briefs and response reasons, are checked before persistence.

The unregistered `handoff-snapshot.ts` prepares private, local worktree snapshots. It resolves tracked changes against HEAD, non-ignored untracked files and explicitly selected ignored globs, preserving final file bytes, executable modes and deletions. It scans every selected file before allocating a snapshot, checks exact copied bytes again, detects source changes with open-file identity/stat checks, rejects symlinks, and removes only its newly allocated staging folder on failure. Cleanup failure is explicit; existing staging data and the source worktree are never deleted or overwritten.

Tracked selection enumerates HEAD and the index using read-only Git metadata commands, then compares raw bytes and executable modes against Git blob hashes. It never uses worktree `git diff`, clean/smudge/process filters or text conversion. Any configured filter driver, skip-worktree/assume-unchanged flag, or selected tracked symlink/submodule makes the repository unsupported; these states are refused rather than silently omitted or rewritten. Late filter configuration cannot execute during raw comparison and is refused at final repository validation. Raw comparisons have a separate per-pass read budget of at least the defaults (1 GiB total, 256 MiB/file), raised only by larger explicit transfer bounds; exceeding it refuses preparation rather than reporting an incomplete snapshot. A tighter transfer limit still applies to the actual selected output.

When `core.filemode=false`, regular tracked executable modes come from a pinned, strictly parsed stage-zero index map; a HEAD-tracked path missing from the index retains its HEAD mode. Physical mode bits remain authoritative when Git trusts them, including the documented `true` default for an absent setting; genuinely untracked files always retain their physical mode. Invalid settings or malformed index metadata are globally refused. Excluded and unselected tracked kinds are not transferred or reinterpreted; unsupported kinds or unsafe paths among included tracked/snapshot paths fail closed. Both selections use the same pinned authority, and configuration/index modes are reread after manifest sync and final repository validation. Any observed authority change fails preparation as `source_changed`, preserving existing staging data.

Receiver verification binds the canonical manifest digest, operation count and byte total to the immutable offer summary, then independently verifies each file's size/hash and reruns the secret rules. A self-consistent replacement manifest is not enough. This helper performs no network, apply or wake operation.

Snapshot Git subprocesses share one per-operation environment, discard inherited repository/index/object/namespace overrides, and uniformly disable object replacements and graft interpretation. Global/system configuration sources are retained for filter checks. Repository replacement refs (including packed refs), graft files and object-alternate files are explicitly unsupported; their presence and the Git/common-directory identities are rechecked during initial validation and after manifest sync, before returning a ready snapshot, without modifying them. Base, branch and remote are also reread at this final boundary. Ordinary linked worktrees remain supported. Late replacement changes cannot reinterpret the advertised original base between checks; any observed unsupported state blocks a ready snapshot.

Root and ancestor identities/stat stamps are pinned across the operation and checked after path lookup, after open before reading, after each read before using bytes, and before returning verification. Open descriptors must still match the current leaf identity. These guards reject observed directory replacements, including matching-byte parent symlinks; they are **not atomic descriptor-relative confinement** against arbitrarily timed concurrent same-user path swaps. Native confinement or an explicit unsupported boundary remains an activation gate; transfer/apply/wake stay disabled, and these helpers must not be presented as complete TOCTOU protection.

These are internal safety primitives, not a complete transfer implementation. Project-owned audited allowlists, branch bundles, resumable transfer routes and automatic fresh-worktree apply remain gated on subsequent reviewed slices. Agents cannot override a secret block. All symlinks are currently refused, including inside-worktree links; there is no cross-platform link recreation yet.

### Capacity foundation (not registered)

`handoff-capacity.ts` exposes only machine fingerprints, presence/timestamps, agent counts, load/disk bands, per-provider availability and the accepting-handoffs flag. Unknown fields, hostnames, paths, process lists and exact utilization/disk counters are refused by the wire schema. Offline computers immediately return an offline record without probing or reusing an online cache entry.

The local sampler reads CPU counters over 100 ms, memory counters and `statfs` for registered project volumes; it never creates files, benchmarks, lists processes or invokes a provider. Load is high at 90% CPU or memory pressure, medium at 65% CPU or 75% memory pressure. Disk is low below 2 GiB or 3% available, limited below 20 GiB or 10%, otherwise ample; multiple volumes use the worst band. Missing or invalid observations fail explicitly instead of claiming spare capacity.

The internal query service shares in-flight reads, caches for 30 seconds, limits callers to 30 queries per minute, checks `device.read` before and after the query, and rechecks the entire result cohort against fresh membership after the final asynchronous grant check. Removed peers fail the query; fresh offline peers return only an offline record and invalidate cached online data. A transport rejection becomes an offline record only when fresh membership actually confirms offline; a still-online failure remains explicit. A peer that reconnects after an offline observation requires a new query rather than invented online metrics. Its membership, grant, pinned-transport and startup adapters remain integration work. No capacity tool/route or settings UI is enabled by this foundation.

Inventory and provider signals remain injected interfaces in this slice. Concrete app sources, the observational quota accessor, runtime activity extraction and the accepting-handoffs setting are not installed.

## Durable agent delivery (#3334)

Every cross-machine `send_message` and `send_file`, online or offline, enters the atomic sender outbox before transport. Supply `idempotency_key` (or `task_id`) when retrying: caller, machine, target, tool and both network pairing epochs scope the key, and different content under that key is refused. Without a supplied key, a new call is new work. Queued responses include `delivery_id`; `get_delivery` reads only the caller's retained delivery metadata. Work from an ended pairing is not sent under a new pairing.

The receiver durably claims the call before invoking its tool and persists a typed receipt before the sender removes it. A replay after either app restarts uses the same ID. `delivered` means receiving-tool/runtime acceptance, **not model processing or completion**. A receiver interrupted between claim and receipt returns `indeterminate` and never reruns that claim. Inspect the target before submitting different work: arbitrary runtime side effects and receipt persistence cannot be one atomic transaction. Native chat busy/starting states retry before accepting input; a race that already queued input is indeterminate, not falsely delivered or automatically resent.

Messages remain ordered per machine. Safe retries back off from one minute to one hour and expire after seven days. The receiver retains dedupe receipts for eight days; the combined store is capped at 10,000 receipts/status rows and 64 MiB, with space reserved for in-flight answers. A full or unreadable store fails closed rather than evicting live dedupe records. Retained answers are bounded to 64 KiB. Wake/reset tools are never automatically queued or retried.

Sender grants, connection switches and peer membership are checked again before each attempt. Refusal, expiry and indeterminate delivery produce a durable pending sender notice and a sender-owned `action_history` receipt (`id: annex-delivery:<delivery_id>`), never an executable Action. Native notice correlation avoids repeating a notice already recorded in the current chat transcript; PTY notice acceptance does not prove a model read it.

Both desktops need delivery protocol version 1 (atomic claim/receipt, boundary `runtime-accepted`). Before every attempt, the sender negotiates it over pinned-member `POST /api/v1/network/agent-delivery-capabilities`; no positive capability cache survives a downgrade. Unsupported peers are explicitly refused before input, with an update-required history/notice; a lost capability answer safely retries before any input. A legacy transport-only HTTP 200 is indeterminate with `missing_durable_receipt` and is never automatically resent. Pending entries migrated from the old outbox are also quarantined: their earlier acceptance cannot be proven. Inspect those targets before creating new work.

## Agent access to Network settings (#3332)

`get_annex_network_settings` requires `settings.app.read` and exposes only switches, effective listener scope, discovery policy and an `expected_state` token. `update_annex_network_settings` changes only `loopback_only`, requires `settings.app.write`, and always asks the person to approve the exact change even when its grant is Allow. Read the current token first; changed settings invalidate pending approval. Expanding exposure is explicitly identified as sensitive. An isolated process profile cannot be broadened by MCP, and application failures are returned explicitly. No device identities, addresses, ports, PINs, fingerprints or peer secrets are returned. The existing settings audit records successful changes.

A successful MCP scope change awaits actual TLS and both listeners under the approved profile, not just a call to start. Stopping or closing a listener during startup rejects the pending change rather than leaving settings writes blocked. A server-owned error listener drains and logs OS bind errors already queued at cancellation, without retrying or stopping a newer runtime. Failed strict starts are stopped without creating the ordinary HTTP error-only fallback. Restoration of the previous saved setting and secure runtime is attempted; a failed write, failed runtime restore or concurrent settings edit is reported as an explicit partial failure, never a successful change or a fabricated complete rollback. A concurrent runtime replacement or intentional disable is preserved; an interrupted rollback does not claim that the previous setting was restored or Annex is stopped.

## Manual connect and user-managed forwards

In **Add a device**, paste the other computer's unmodified pairing link. **Address override (optional)** accepts a host or `host:port`, for example `127.0.0.1:7443` for a local forward or `[::1]:7443` for IPv6. Omitting the port uses the main TLS port from the link. An override replaces the link's endpoints for that pairing attempt, not its expected identity, certificate or one-time PIN.

The port must forward to the remote computer's **main TLS port**. The plain-HTTP identity-hint port only provides an untrusted discovery hint; pairing and control never use it. No identity-hint override is needed.

Without a pairing link, choose **Pair without a link** and enter the address with its main TLS port, the six-digit one-time code, and the full SHA-256 **Certificate fingerprint** from the other computer's Pairing link section. The fingerprint is selectable and copyable there; the short certificate code is not enough. Annex checks the expected certificate before sending the one-time code and pins it again for the pairing request. A mismatch sends no code. Successful pairing, membership and reconnect use the same flow as pairing with a link, with no wire or mobile contract changes.

For example, start a user-managed SSH forward with `ssh -N -L 127.0.0.1:7443:127.0.0.1:<remote-main-TLS-port> <remote-host>`, then pair using `127.0.0.1:7443`. The transport must pass TCP bytes unchanged. TLS-terminating proxies are unsupported: Annex checks the certificate named in the link before sending the PIN, then pins that certificate on every connection. Loopback clients gain no special trust and still authenticate with their paired certificates.

The reached address and its port are remembered alongside the link's direct addresses and their original port. Loopback remaps never replace the legacy default port. Reconnect works without mDNS after restarting Clubhouse and retries with normal backoff when a forward drops and returns. Clubhouse does not start or manage the forward. A refused or unreachable loopback connection suggests checking that the local forward is running. Manual loopback forwards and locally remapped ports are not advertised to other network members. Membership-announced listening endpoints are kept separately (`announcedReach`) and shared with their announced port, including loopback endpoints for same-host setups. The mobile and membership wire contracts are unchanged; each exported host uses that record's single port.

Membership announcements keep saved loopback routes even when the remote computer lists many direct addresses. After using an older build, a direct address tries its saved per-address port first and the legacy default afterward if it differs; a successful connection updates the saved port. Loopback addresses never borrow that fallback port.

### Only accept connections from this computer

In Settings > Annex Network, **Only accept connections from this computer** binds the main TLS listener and the untrusted identity-hint listener to `127.0.0.1` and turns off mDNS advertising and browsing. Other computers on your network and your phone can reach this computer only through a byte-transparent forward you set up. Clubhouse does not manage that forward. Saved addresses still work for outgoing connections.

The setting is off by default and is saved as `loopbackOnly` in `annex-settings.json`. Changing it restarts the listeners and refreshes discovery without removing paired devices or changing their certificates. Turning it off restores normal listening and discovery, unless an isolated test profile restricts networking. Existing settings without the field keep their current behavior. Annex settings are not mirrored to the phone, so the mobile contract and fixtures are unchanged.

Restarting closes every incoming connection, including unfinished TLS handshakes and requests. A previously connected phone or computer needs a forward to reconnect while this setting is on. Existing outgoing connections stay open.

## Real-device checks

Synthetic tests can't cover certificates under Electron or local network discovery, so each stage merged on green CI and these checks wait for real devices before a release. They're written as one script to run in order: each part says what it starts from, each step says what to do, then what you should see (✓). The issue in brackets is where the behaviour was built, for filing anything that fails.

### What you need

- Two computers, **A** and **B**, both on a build of main and on the same Wi-Fi. **A** should be a Mac. A Windows PC as **B** covers the most.
- On both computers, the same git repository open as a project, plus one folder with no git remote. Both need a chat agent and the Dispatcher.
- A tailnet (or another VPN that gives names) that A, B and the phone can all join, and a second way for A to reach the internet (a phone hotspot or wired network) for step 2.2.
- A way to block local discovery between A and B: mDNS off, or different subnets.
- A phone with today's Clubhouse Go. Step 7.7 installs an older build that sends the desktop's name over it, so reinstall today's app (or the new one) afterwards. Part 8 waits on the iOS app adopting the phone contract in `docs/annex-network-phone.md` (#3062), pairing ids included.
- Optionally, a third computer **C** for Part 9. Nothing before Part 9 depends on it.
- The app log is in `~/.clubhouse/logs`. Computers pair by pasting one's **Pairing link** (Settings › Annex Network › Add a device) into the other's **Pair with another computer**, or by picking it from the computers found on the network. The QR code is for the phone.

### Part 0. An existing pairing (only if you have one)

If A or B still has an Annex pairing made before stage 4, check it first, since everything after replaces it.

1. Use it as before. ✓ It still works one-to-one, and the controlled computer shows "Controlled by". (#3061)
2. On both computers, use Settings › Annex Network › Reset Annex Network, then Confirm reset.

### Part 1. Turn it on and pair

Starts from: A and B connected, and C with Annex Network on and no devices.

1. Turn B off. On C, paste A's pairing link. ✓ A's Settings shows C's join waiting on B. Turn B on. ✓ B lists C and connects to it, with no pairing made on B or C, and the waiting line goes from A. (#3061)
2. On B, remove C. ✓ A and C hear at once, and C leaves the network. (#3061)
3. On C, paste A's link again. ✓ B lists C again. Turn B off, then on A remove C. ✓ A's Settings shows the removal waiting on B. Turn B on. ✓ C is gone on B too, and the waiting line goes. (#3061)
4. On C, paste A's link again. At least five minutes after B last paired, set C's clock two minutes behind. On A, remove B. On B, paste C's pairing link, so C makes the new pairing with its slow clock. Quit and reopen all three. ✓ B stays in the network on all three. Set C's clock back. (#3107)
5. Turn C off. On A, remove C. ✓ B hears it. Turn A off. Turn C on, and on C paste B's pairing link. Turn A on. ✓ C stays in the network when A's old removal reaches it. (#3107)

A phone vouching for a device keeps the pairing it carries, unless a removal on that desktop ended it. A record moves a member's pairing only with an id: the one it hadn't learned yet, or a later pairing. A desktop's own stamp, or a member's own clock, never moves it, and a member's record of this machine never moves this machine's own pairing. A removal names the pairing it ends (`pairingId` and its `joinedAt`), and ends that pairing or an older one, never a later one; a record with no id counts as the one named. Records from before carry no id and compare by time. Every network message already carries `v: 1`. The phone contract (#3062) says the same, and a four-machine simulation of these flows is a permanent test. | The membership protocol hadn't shipped, and the phone side isn't built: the cheapest moment to change the record. Join times alone weren't stable across members, and an id minted on both sides of a pairing split. | Two pairings of one device made within clock skew of each other (they're still ordered by join time); a re-pair between two machines that both missed a removal keeps the removed pairing, so the removal still wins. |


## Dispatchers across the network

Computer members publish their hidden Dispatcher controllers and derive two-way coordination links. Each receiver triages remote work under its own grants. A person may choose a network lead for a shared conversation; local controllers and memory stay on their own computers. Offline delivery, explicit outcomes, manual Take back and human-only approval routing are described in [Federated Dispatchers](dispatcher.md#federated-dispatchers-2834). See the [controller-link and remote-request terms](glossary.md).

## Reading another agent's configuration

`read_agent_config({agent, project?})` is an ordinary-agent MCP tool. An agent can name a local id or unique registered name (optionally scoped by project), or an `agentId@machine` address. Its `agent.read` grant is checked on that target: connected by default, or the Dispatcher's ANY. It returns desired managed instruction text and ordered instruction/skill/MCP parts with their content, revisions and provenance. Unmanaged agents expose only their own registered provider instruction file. Catalog source distinguishes built-ins, custom user/copy parts and imported/plugin library parts. This is configuration evidence, never proof that a running provider loaded it.

Remote reads use the existing pinned-member `POST /api/v1/network/agent-call` transport, computer membership and pairing checks, and rate limits. The receiving host checks `decideGrant(caller@machine, agent.read, target)` too; Ask first is refused there. Ordinary remote callers still need a stored connection and honor its disabled tools. The sole connection exception is **read_agent_config from a current member's authenticated federated Dispatcher controller** (the pairing-bound federation identity, never the claimed name). That identity supplies only the normal Dispatcher `agent.read` ANY default to this read's host-side decision; the person's saved host grant changes apply over it. It adds no write, message, wake, reset or migration permission. Membership, federation identity, connection switches and the host grant are checked again before configuration bytes are returned. An offline computer answers offline immediately; reads never queue or persist configuration in the input-delivery ledger.

The configuration JSON is capped at 256 KiB, 32 KiB per text/string, 100 parts and 100 entries per content collection. Truncation is explicit; a saved setup with more than 100 references is refused before content resolution. Missing parts are reported. The tool never materializes files or runs a provider, and does not read grants, connections, sessions, authentication or global provider configuration. Skill bundles include supporting files; truncated content is inspection data, not an importable bundle. Portable config migration is a separate design in #3481.
