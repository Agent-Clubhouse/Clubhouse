## Actual source findings

- `annex-handlers.ts:applyNetworkSettings` returns void. Its server enable/rebind calls start(), which schedules startServer and returns before listeners are confirmed. The local SAVE handler awaits persistence, then calls this void function. That return cannot prove runtime success. Existing local save behavior is source context, not a newly executed baseline defect.
- `annex-server.ts:startVerified` already awaits strict startup: captured TLS+pairing listeners must both be current/listening with positive ports and matching effective profile. Its AnnexStartFailure uses the existing serverGeneration to stop an owned failed attempt and avoid stopping a replacement. Reuse that ownership; no second server lifecycle generation.
- `getStatus().tlsEnabled` means a TLS object exists, including during pending bind. Port/status/hash equality after an await is not ownership of the runtime or settings intent that initiated it.
- Existing MCP forward/restore uses startVerified plus wasSuperseded. Its deliveryHash comparisons are still equality, not the r3 exact owned committed field/version receipt. Those consumers require the separate r3 migration, preserving grant/Ask/no-op semantics.
- Client start/stop orchestration is synchronous; startDiscovery catches/logs errors. There is no aggregate client-runtime generation equivalent to serverGeneration. Satellite connectionEpochs, #3733 snapshotReceipt/connectionGeneration and controller-read revisions are different scopes and must not be reused as proof of client runtime ownership.
- annexNetworkProfile can enumerate interfaces for an explicit selected-interface profile. Do not call it, getSettings, getStatus, identity/TLS loaders or any other IO-capable helper from the proposed pure listener predicate. Compute the existing validated desired profile in the admitted caller, over actual committed settings, then pass its expected host. A secure-listener receipt makes no mDNS/discovery/remote-connectivity guarantee.

## Proposed server hunk and exact ownership result

The proposed additions are fully shown in secure-listener-functions.review.ts.txt. secure-listener.review.patch.json wraps exact patch bytes (to preserve whitespace) against the bound server source; they are **not applied**. Only a new append next to startVerified/before startServer is proposed. No existing start/startVerified/stop/listen/default caller body, timeout, retry, cleanup ordering or shutdown/update policy is edited by the patch.

`captureSecureListenerReadiness(expectedHost):()=>boolean` captures private generation, exact TLS/pairing objects, ports and host. It latches actual ready-at-capture, checks current listening state plus unchanged identities/generation/ports/host, and returns false forever if captured unready. It is pure memory observation: no IO/await/timer/emits, settings lookup, grant or network probe. Existing production lifecycle changes rotate serverGeneration through start/stop; raw close sites are private stop/listen-error cleanup. Required tests still need to establish behavior across those paths; no claim that the predicate cancels/drains entered OS work.

`startVerifiedWithReceipt(expectedHost):Promise<()=>boolean>` opts into the existing verified attempt. It captures identities/generation immediately after the synchronous start invocation and before awaiting; after strict verification, it rechecks those original objects/generation. A replacement is never adopted even if settings/text/ports match. **Then check boundHost against the original expectedHost separately.** A mismatch throws typed AnnexStartFailure with interrupted=true (superseded/unconfirmed), without STOP/rollback or refreshing expectedHost/admission. Same generation/objects do not prove ownership of the expected profile: MCP updateSettings runs outside the handler settingsWrites chain and can commit a new profile between the original commit and this start. Strict startup can correctly bind that newer profile; this old continuation must leave it running.

Only after identity/generation **and original expected host** match may a false ready predicate represent genuine owned listener/port loss. In that narrow case the proposed helper stops the still-owned failed attempt and throws AnnexStartFailure after the generation bump. No await exists between those checks and cleanup. Existing startVerified failure cleanup remains unchanged/delegated. A false capture predicate by itself is **never unconditional STOP permission**. This behavioral cleanup requires independent corrected source review and later executed controls; patch applicability is no clearance. No expected-profile parameter/precondition is added to strict startServer/startVerified; that separate expansion is not proposed or approved.

The receipt is main-process internal and must not be serialized into an IPC DTO. It confirms local secure listener ownership for an expected binding, **not** sender/epoch/commit/intent authority. A capture of an already-starting server cannot become valid later. A fresh explicit enable/retry obtains a fresh operation receipt and, when needed, a fresh verified attempt. No auto-retry, new policy halt or delayed activation by equality.
