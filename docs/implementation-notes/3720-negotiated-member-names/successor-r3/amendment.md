## B1: emergency persistence has three primary-base states

Immediate live-off remains synchronous before any persistence or reread await. The durable emergency turn runs on the **actual existing store pendingWrite**, not merely the handler's settingsWrites chain and not a second queue.

| Primary outcome/base | Durable emergency composition |
| --- | --- |
| Known committed, public tuple healthy | Compose the explicitly authorized off/reset fields on the known actual base under existing guards. |
| Known committed, public publication failed | Compose on the retained **actual primary base/receipt**, preserving the accepted change while writing off. Never use the older degraded public tuple. |
| UNKNOWN primary outcome or unknown actual base | Before composing anything, perform the same strict validated primary-file reread used by controlled recovery, **inside this same pendingWrite turn**. Compose off only on that validated actual base. |

The UNKNOWN reread uses the fixed private settings path, bounded plain-file/provenance checks and complete shape/private-witness validation; missing, unreadable, malformed or changing-during-read input fails. It does not invoke the legacy loader, fallback defaults, migration/backup writes, temp sweep, name initialization or equality-based intent adoption. Recheck original emergency/launch/settings scope at turn, after read and before primary replacement. A newer emergency/reset supersedes the old continuation rather than letting it overwrite a newer state. Existing file replacement/precondition/retry behavior is unchanged.

If the strict reread fails, perform **no emergency disk write**. Return an explicit durable-persistence refused/unconfirmed result while retaining the already-observed live-off and degraded owner status. Never substitute a stale public tuple, last attempted candidate, guessed default or matching Alias text. A later authorized explicit attempt remains possible.

A successful UNKNOWN reread establishes an internal validated base for the emergency mutation only. It does **not** heal the public versioned surface, create a new public settings epoch, prove prior per-key version lineage or activate any name intent. Persist the authorized off/reset fields on that base, preserving all other validated values and existing selective-purge semantics. Report primary emergency persistence separately from unavailable public currentness/name activation. Public versioned recovery still requires the explicit privileged recovery action. A failed emergency replacement remains unconfirmed/unknown as appropriate; no fake rollback. Process-level receipt is not a power-loss guarantee.

Required discriminators: (B1-a) uncertain outcome then valid reread of B then emergency writes B+off; (B1-b) same with missing/unreadable/malformed/changed reread means zero replacement, live-off retained; (B1-c) known publication-fault base B composes without stale A; (B1-d) held reread then newer emergency/reset refuses old write; (B1-e) neither branch publishes a healthy tuple/new epoch or activates a pending name by equality. Mutation to legacy-loader/default/candidate composition must fail these controls. These are proposed tests, not executed results.

## L1: fresh execution is distinct from duplicate/status lookup

Replace the permanent 32-invocation-per-degradation cap. Bound **one in-flight execution** and **32 recently completed records globally**, evicting oldest completed records first. Never evict in-flight work. Failed completions can be retired/evicted and never prevent a genuinely fresh retry. No unbounded request-ID map, historical tombstone set or lifetime32 lockout.

The main process owns ordinals and a single currently eligible **admission ticket** in the active degradation scope:

1. Creating a degradation scope creates a random degradationId and one random ticket/requestId, with an internal next ordinal. This occurs in the fault/status transition, never in GET/display. Status reads only reveal existing readiness/ticket; they allocate nothing.
2. A FRESH user action sends strict `{mode:'execute', degradationId, requestId:ticket}`. There is **no renderer-supplied ordinal**. The main validates/captures current real caller authority first. Only an exact match to the current main-issued ready ticket, in its active scope with no in-flight work, may be consumed. Main synchronously consumes that ticket and allocates the internal ordinal **at invocation entry before queue/IO**. The request identity is permanently that consumed ticket within that scope; replay cannot allocate another ordinal.
3. After a failed completion, store its bounded recent result and create a different ready ticket for a subsequent **explicit** fresh action. Do not automatically submit it. A replay of the old requestId does not match the new ticket and cannot become a fresh execution, even after its result record is evicted. The integer ordinal is internal metadata only. Before issuing a ticket whose ordinal would exceed Number.MAX_SAFE_INTEGER - 1, main rotates the recovery-attempt/degradation scope id, starts its ordinal at1 and records that pure status transition; existing completed records remain globally bounded. This happens at completion/admission bookkeeping, never in GET, and does not heal settings or change the public settings epoch. Never reuse an ordinal within one scope.
4. A DUPLICATE/STATUS action sends `{mode:'status', degradationId, requestId}` and can never consume a ticket, allocate an ordinal, reread or rotate an epoch. After authority checks, an exact known in-flight request joins its status/promise, and an exact recent completion returns its recorded result. `mode:'execute'` with the same retained consumed ticket also returns that same status/result without executing again.
5. **Authority first, retained duplicate lookup next, healthy short-circuit afterward.** This permits a known successful duplicate after recovery to receive its prior completion without another reread. Original caller-document binding is checked before sharing a retained result; IDs are not grants. A fresh healthy invocation returns not_degraded without IO/ticket allocation/rotation. A missing retained status/consumed request returns typed not_retained, never silently executes as fresh.

Concrete missing-record result table (after real authority and known lookup): status mode always returns not_retained; execute mode with healthy/no active scope returns not_degraded; execute mode with active degraded scope but a nonmatching/consumed/unretained ticket returns not_retained. Every row has zero reread/rotation/execution. These results deliberately do not reconstruct whether an evicted ID was previously seen. Only exact ready-ticket execute admission can create a new execution.

The bounded recent record contains degradationId, main-issued requestId, allocated ordinal, original document binding, safe result/status and result ownership; it does not retain raw unrelated settings or arbitrary caller objects. A ready ticket plus one in-flight record and the global32 recent records are the entire lookup state. After eviction there is deliberately **no distinction between expired and unknown IDs**: not_retained, no reexecution. A current fresh ticket is recognized by exact equality to the one stored ready ticket, not by assuming every unknown request is new. An old request modified to carry the new ticket is a different explicit attempt; the unchanged replay cannot obtain one automatically.

Successful reload ends the degradation scope and clears its ready ticket. Keep its recent completion in the same global bounded cache; known old duplicates return recorded status, unretained ones get not_retained/not_degraded without IO. A new fault has a new degradation scope/ticket; an old request cannot enter it. Reset/main restart discards ephemeral lookup state and changes the existing settings scope: prior unknown results cannot be reconstructed and return not_retained/stale-scope, never execute. No persistence of recovery IDs or claim that the floor survives process loss. Within a live scope, ticket consumption/floor never moves backward; healthy transition does not revive a consumed ticket.

The renderer recovery action owns a new session/action generation **before its first await**. The exact ticket/scope/action receipt gates every completion, status/error setter and cache adoption. Random epochs are not lexically ordered. A not_retained response may prompt reading committed **status**, not auto-reread/heal or autoexecute using a fresh ticket. A fresh human retry obtains the already-advertised next ticket under a new action receipt. Late/evicted old replies cannot overwrite a newer recovery/healthy/reset result or clear a newer draft/error.

Required discriminators: L1-a 40 sequential failed rereads then success using fresh tickets; L1-b duplicate pending joins, no second read; L1-c recent failed/successful duplicate returns recorded result before healthy shortcut; L1-d evict first of >32 completions then replay exact old execute/status gives not_retained and zero IO/rotation; L1-e old ticket+new/forged ordinal rejected (ordinals not a request field); L1-f status mode with ready ticket cannot execute; L1-g one in-flight globally, completed eviction does not evict it; L1-h reset/restart/new fault fences old scope; L1-i late evicted response cannot update renderer status/error/cache. These are proposed tests only.

## C1: every affected post-await setter needs current ownership

`acceptLoad`/`failLoad` followed by an unconditional status/error setter is invalid. Place settings **and status** publication in the same admitted callback, and place error publication in the admitted failure callback. Those callbacks execute only for the current load/session/request ownership, not merely because helper invocation returned. `submit` success/error callbacks have the same ownership requirement. No outside continuation may write status/error after a rejected/stale load.

SettingsView's `setSettingsLoadFailed` after `await saveSettings` must also check the captured session/action generation, component lifetime and latest relevant action sequence, or run only in an explicitly admitted callback. A newer action/reset/recovery/unmount suppresses the old success **and** failure setter. Purge/recovery take ownership before await; all affected subsequent status/list/settings/error setters are similarly gated. The corrected scaffold shows these boundaries, but session/draft ownership helpers are still unimplemented. Untouched methods are not implicitly proven safe by this scaffold.

Controls: older load accepted/rejected after newer success; stale error after new edit/reset; save completion after newer View action/unmount; purge/recovery old completion after new scope; rejected helper callback with external setter spies. No stale status/error update, draft clearing or cache rollback. Reintroducing the unconditional setter must make the negative fail.

## C2: preserve UI audit attribution and capture the original event

Keep `withValidatedArgs` and its existing `withSettingsSurface('ui')` scope (or an exact explicitly reviewed equivalent). Settings audit attribution is separate from authority; a claimed payload origin never grants UI/main-window trust. Do not alter the shared validation wrapper/default callers.

The outer IPC entry handler synchronously captures the **original event sender object, main-frame object, URL/document incarnation and runtime admission before validation/queue**. This capture may be an invalid receipt; naming authority is demanded only where the contract requires it. A per-invocation validated wrapper closes over that receipt, rather than recapturing a later event/window/frame. Recheck captured identity/current authority at the queued/commit/pre-rename/post-await/runtime/name ACK boundaries. Preserve AsyncLocalStorage UI attribution across the returned queued promise; invalid/refused calls get fixed-code refusal logging with the same descriptive surface and explicit refused caller status.

Use typed `invalid_envelope` for unsafe/incorrect outer shape, wrong argument count, descriptors/clone failure or untrustworthy correlation. Return a bounded refusal with requestId null rather than echoing untrusted data. For an otherwise safe envelope with a validated UUID correlation but invalid key/type/value/origin/local version, use typed schema_invalid and that safe requestId. Plain parser Error is **not** typed IPC refusal. Both paths enqueue/write/publish nothing, dispose only their entry receipt and log fixed route/code/caller-trust metadata only—never raw Alias/payload/prototype/credentials. Unexpected errors remain honestly unconfirmed where commit might have occurred.

Controls: UI audit surface present for successful and queued writes; invalid envelope/schema returns typed refusal rather than transport-only Error; original event/frame changes during validation or before queue do not acquire authority; same URL revisited cannot revive receipt; invalid schema has no settings/name/write/event; no raw hostile property getter invoked just to log a refusal.

## C3: exact descriptors and clone-safe typed construction

For ordinary objects, validate the prototype policy (Object.prototype or null), **all Reflect.ownKeys**, and each own descriptor. Mandatory/allowed keys must be own enumerable data properties; reject symbols, accessors and extra keys including nonenumerable extras. Object.keys alone is not exact. Validate nested base/fields/changes likewise before reading descriptor values.

For unset, require an actual array with the ordinary Array.prototype, bounded length from its own data length descriptor, and exactly the own keys length plus indices 0..length-1. Every index is an own enumerable data string value; reject custom own non-index properties, symbols, accessors and altered prototypes. Do not call raw `.some`, iterator, spread or other user-controlled methods. Holes already fail the old implementation after spread yields undefined—**do not invent a missing-hole baseline defect**. Keep a hole negative as a preservation control; actual gaps are descriptor/prototype/non-index/nonenumerable cases.

After validation, construct a fresh typed DTO explicitly from checked primitives, typed per-key assignments and newly constructed dense arrays/maps; no `as unknown as LocalSettingsPatch` stands in for proof. Check byte bounds on the canonical constructed DTO; reject any descriptor/clone failure with a fixed typed envelope error. Preserve local schema/origin semantics and no member-wire/mobile changes.

These rules specify shared-parser strictness for direct inputs. Electron structured clone may reject/strip some hostile inputs before the main parser, and cross-realm/proxy reachability must not be guessed. Direct parser negatives do not prove an Electron IPC exploit. Test actual clone behavior separately if any reachability claim is made. No promise that portable shared reflection detects every Proxy trap; IPC clone boundary and genuine caller authority remain independent gates.

Controls: nonenumerable extra top/base/changes keys; getter with zero invocations; symbol/custom own array property; own index accessor; altered array prototype; standard dense/frozen-data arrays; holes preservation; canonical typed clone without unknown casts; real Electron clone behavior only if claimed. Strict parser/API helpers remain unimplemented product work.

## Startup and runtime-readiness limits

Normal startup establishes the committed tuple/epoch/version cache before IPC/channel use using the existing normal settings load; GET/display remains pure over that established state and never heals degradation. Startup defaults are not controlled recovery from missing/invalid bytes. The future implementation must prove startup ordering, rather than moving initialization into GET.

Existing `applyNetworkSettings` returns void, calls an unverified server start and catches/logs start failure. Its return cannot establish successful runtime readiness. A committed settings result must separately state runtime applied/unknown/failed using actual owned readiness/failure evidence; errors/uncertainty are committed_unconfirmed, never false settings rollback. Original admission/owned-version/wasSuperseded checks still fence all effects, including late STOP. This does not authorize a new listener policy or broader lifecycle rewrite; the exact implementation/readiness seam remains independently reviewed.

All proposed implementation pieces still need exact writer clearance, deterministic red/green and the required matrix/type/lint/source review/hosted checks. The launch source approval remains source-only and unchanged. No test execution or implementation acceptance is created by this amendment.
