## R-a: exact string validity

The version-1 naming trim set is exactly these Unicode code points: `0009–000D`, `0020`, `00A0`, `1680`, `2000–200A`, `2028`, `2029`, `202F`, `205F`, `3000`, `FEFF`. Trim maximal runs at both ends, not interior runs. This is the ECMAScript trim set, fixed explicitly for implementations in other languages. `0085` and `180E` are **not** trim characters; do not substitute Go `strings.TrimSpace` or a locale-dependent rule. No NFC/NFKC or case normalization applies to the name.

Local writers validate the original string for well-formed Unicode, perform that exact trim, then require 1–200 UTF-16 code units. A supplementary-plane scalar counts as two. Refuse overlength names; do not use `slice(0, 200)` or replace lone surrogates. This applies to UI Rename, local Alias intent, USE_LOCAL_ALIAS and agent Rename. Hash only the resulting exact name. A modern receiver requires the transmitted name to be well formed, nonempty, at most 200 code units and already trimmed under this rule. An untrimmed modern record is invalid, not silently normalized before its hash check. A malformed modern extension frame is refused with 4400 under the strict codec contract.

The raw owner's Alias preference is distinct from the trimmed network name. Alias-intent detection compares the existing effective preference expression `alias || deviceName || 'Clubhouse'` before and after a save; validate/trim only when an actual change would create a name operation. A non-name save with an unchanged legacy preference does not start name-store work or fail because the old preference is malformed. USE_LOCAL_ALIAS validates the currently stored preference explicitly and can refuse it visibly. New UI input must satisfy the naming rule before it can publish an intent. Pairing invitation fields remain preference based.

## R-b: invalid legacy event is visibly skipped

Keep the old v1 parser/connection behavior. After an authenticated current legacy `member-renamed` passes that parser, the naming adapter applies the same well-formed/already-trimmed/1–200 validation. If invalid, **skip the name event visibly**, preserving the current ordered or baseline name, logical clock and legacy replay floor. Do not convert replacement characters to a verified record, advance a floor, silently claim application, or close a valid v1 channel for this adapter failure. The sender's permitted subsequent membership/reach messages still work.

Example: the old writer can truncate `199 × 'a' + U+1F680` to `199 × 'a' + lone high surrogate D83D`. JSON can carry the escaped surrogate and the old string-length validator accepts it; the naming adapter must not mint a hash for that ill-formed value. The fixture represents this with `\ud83d`, not an invalid UTF-8 file.

A bounded local name-health status records a fixed reason code (`legacy_name_invalid`, `epoch_limit`, `store_unavailable`, or `clock_range`) and a count capped at 256. It never retains or logs a rejected raw name. Expose that status in the local Alias/name surface with a local-only read/event, not extra legacy wire fields, Settings writes, controller revisions or network retries. An authenticated legacy sender gets no naming success ACK because v1 defines none. Agent/local callers that cannot commit get failure. UI copy must not promise that all legacy peers accepted a rename.

## R-c: main-app naming caller trust and rechecks

Add a narrow independent main-process name-UI authority seam; do not reuse plugin issuers or import the refused federation machinery. Configure it in `main/index.ts` adjacent to existing main-window host registration with a dynamic getter of the **actual main WebContents object** and `MAIN_WINDOW_WEBPACK_ENTRY`. This new registration/import and its test are proposed hunks pending review.

A captured IPC authority receipt requires all of the following at entry and at every guarded commit/ACK:

- The sender is the currently registered main WebContents object, not merely the same numeric id, and neither it nor its BrowserWindow is destroyed. `BrowserWindow.fromWebContents(sender)` must be the registered main window owning that object.
- `event.senderFrame` is the exact captured main frame and equals `sender.mainFrame` now. No subframe, plugin/webview, popout or another window is eligible, even with an identical URL.
- The frame URL equals the configured entry URL after URL parsing/serialization. Compare the complete `new URL(url).href`, including query and fragment; do not accept origin/prefix/path-only equality. Invalid or unavailable URLs fail closed. An entry URL in tests/development is the actual configured entry, not a hard-coded production origin.
- The sender's document/navigation generation is unchanged since capture. Invalidate on a main-frame document navigation, render-process replacement/gone, or destruction, so navigation away and back cannot revive an old receipt. Observe existing Electron events solely for this authority receipt; no startup/stop/client lifecycle changes. Same-document navigation is also invalidating for a pending receipt.

Capture is synchronous and may return an invalid receipt without throwing. SAVE_SETTINGS demands it **only if the queued effective preference actually changes**, before reservation and at the settings atomic replacement. RENAME_DEVICE and USE_LOCAL_ALIAS always demand it. Non-name saves keep their existing caller policy. No URL supplied by a renderer can configure the authority host.

The `SettingsCommitPrecondition.prepare` used here is bounded and fail-fast: an already-resolved no-IO step; `check` synchronously re-evaluates the receipt and relevant target bindings. It must not wait for a window, load stores, prompt, poll, or hold a lease. Use the existing atomic replacement checks on every replacement attempt, including Windows' existing retry path; add no retries or delays. Recheck after each awaited boundary and immediately before activation/publication/success reply. Refusal after a durable operation has committed is reported as unconfirmed to that caller; do not roll back a newer name or claim no write occurred.

Agent Rename retains the existing `device.manage` registration and audit actor. Extend only the internal `DeviceToolHost.rename` argument with `assertAuthorized: () => void`; pass it through membership into name-store commit/ACK checks. Its closure captures this host, selected target epoch and original caller identity/context. Re-evaluate current caller access and the exact original grant/args using `checkToolGrant`, `grantApprovalContext` and `callGrantIsApproved`, including the existing consumed Ask-first approval and approval version. A fresh refusal or changed policy/caller context wins; do not request a second approval or set `askHandledByTool`. A replaced host, stopped/replaced caller incarnation, changed target/pin/pairing/role, network departure or off state cannot use an old callback. The remote transport separately rechecks its own current pinned member/socket/epoch. Awaiting the host is necessary but does not replace these checks. Review the concrete internal callback/source proof before implementation; no grant-policy or tool-registry rewrite is proposed.

## I-1: one existing settings queue, exact transaction order

The adjacent `unsafe-precondition-only.review.patch.json` (exact patch bytes in a JSON wrapper) preserves the **rejected, unapplied, unexecuted initial sketch**, not an apply-ready correction or implementation proof. The replacement patch is also unapplied and unexecuted; it contains proposed shared-store/wrapper/handler/MCP/index hunks, not a complete naming implementation. Do not apply it before P7w race review and required-item approval.

Keep `requested = structuredClone(settings)` at handler entry. Capture the UI receipt synchronously then run all intent work inside the existing `settingsWrites.then(apply, apply)` chain. In the queued apply:

1. Read actual current settings; compare the effective preference. For a name change only, check UI authority/target epoch and durably reserve the original stamp/id/pending intent. A concurrent name merge has its own store serialization; reservation and activation retain the same operation, never promote it past a later remote winner.
2. Persist the single explicit requested field patch through the proposed opt-in committed-state atomic path, rebasing untouched fields and rejecting conflicts as defined in `committed-composition.md`. The precondition-only wrapper sketch cannot safely do this. In principle: Pass an optional precondition **only for an actual name-changing save**. `annex-settings.ts` merely forwards the optional existing precondition; default saves, migration, audits and rollback behavior stay the same.
3. After persistence, use the actual committed before/after pair (not stale requested snapshots) and the emergency supersession rules in `committed-composition.md`; otherwise emit existing `settingsChanged('annex')`, then call the existing `applyNetworkSettings(requested, previous)` unchanged. Preserve synchronous network-off controller-read retirement, runtime start/stop/rebind and autoReconnect ordering exactly.
4. Recheck UI/epoch authority and activate the exact reserved operation durably, then refresh permitted display events/publish and reply. If a newer winner exists, do not overwrite it; explicit success means the intent was durably handled, not that no concurrent newer name can win.

USE_LOCAL_ALIAS joins **this same queue**, reads current stored preference in its turn and commits metadata-only intent. It does not call settings save, settingsChanged or applyNetworkSettings. No second settings queue, reentrant wait on settingsWrites, or global lock around unrelated saves is added.

Failure semantics are phase specific:

- Invalid authority/validation, cap/store failure or reservation failure: no settings save or activation/publication; return failure. A non-name disable/stop save never touches name health and still proceeds on its existing chain.
- Settings save/precondition failure: return failure, discard/invalidate the reserved intent without activation/publication. If cleanup persistence fails, retain the error visibly and do not ACK; recovery still requires the expected after-value and epoch. No invented successful rollback or fresh stamp.
- Settings already persisted: always run the existing settingsChanged/runtime apply phase; an authority failure after the save must not bypass security disable or lease retirement. If apply throws, or later activation/ACK fails, return explicit **name unconfirmed** and preserve the original pending intent for recovery. Do not roll back unrelated settings/runtime or suppress a completed runtime apply.
- Recovery requires the exact accepted intent witness described in `committed-composition.md`, plus matching after-preference and epoch; text equality alone is insufficient. It never assigns a fresh stamp. It is a recovery of a previously authorized durable transaction, not an old IPC receipt kept alive across restart. If settings write outcome cannot be disambiguated after a failed cleanup, report unconfirmed rather than falsely claiming no possible recovery. A changed preference/epoch discards it.

Required race cases: two cloned Alias saves in order; Alias save followed by network/client/server disable; Alias+disable in one save; non-name save with failed name store; USE_LOCAL_ALIAS interleaved on the same queue; held atomic flush with navigation/sender replacement; save failure/cleanup failure; post-save activation failure; remote newer rename between reserve and activate; crash at each durable boundary. Verify exact existing settings/runtime call order and lease retirement, not only final values.

## Bounds, skew and initialized-store loss

Epoch cap is 256 retained name epochs, not 256 arbitrary frames. At capacity refuse a new epoch visibly (`epoch_limit`), without eviction, clock advance or dropping existing ordered records. Existing-epoch updates continue. Removal can prune only ended epochs while retaining the clock. Frame/state snapshots remain additive and bounded as frozen contract specifies.

Accepting an operation at `now + 24h` can ratchet this node's durable floor. Its next local edit at that floor + 1 may be more than 24h ahead of a slower peer and get skipped there until wall time catches up or an explicit valid new edit is made. Do not clamp/re-stamp a relayed record or lower the durable clock to force convergence. A boundary and slow-peer fixture must make this divergence visible, and valid other records on the same page still apply. Accepted disk records survive a later wall-clock rollback. This is the explicit clock-skew limit of the design, not an all-clock convergence promise.

Proposed initialization anchor: preserve an immutable `memberNamesStoreId` in existing private `annex-network.json`, matching the dedicated name store's id. Normal startup reads actual source status before default merging; display does none of it. First initialization is allowed only with no anchor and no name file: atomically create a virgin name file (format1/id/clock0/no records/no pending), then durably save that anchor through the existing membership store. During this asynchronous first initialization, naming remains unavailable and no name mutation is accepted; strict v1 connection semantics remain available. A restart with no anchor and an exactly virgin valid name file can finish anchoring the same id. A nonvirgin unanchored file is unconfirmed/degraded, not adopted as a fresh verified clock.

With an anchor, missing/corrupt/mismatched name state is degraded and refuses name writes. No silent defaults/clock reset. Validate that the membership source itself was readable; unreadable membership state cannot be treated as virgin merely because default merging removed the anchor. Preserve the anchor through all membership state copies/saves, including reset paths; changing membership must not erase ordering history or reinitialize identity. This is a naming-only field in the already reserved membership module, not a Settings grant. If **both** the name file and all membership/anchor history are erased together, first run and prior loss cannot be distinguished; this is an explicit evidence boundary, not loss detection. No automatic deletion/repair/install or broad persistence refactor is authorized.
