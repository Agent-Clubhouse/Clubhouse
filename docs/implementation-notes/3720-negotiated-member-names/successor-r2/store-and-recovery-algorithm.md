# Chosen commit-turn and recovery algorithm (supersedes earlier observer placement)

**Source-contract review only; all new helpers below are unimplemented.** No API signature or patch scaffold proves this algorithm. The exact source binding is main `50cb77ab6ccf9f383a39e59db308f4f8336051ea`. Independent shared-store/P7w/lifecycle review and later executed discriminators remain required.

## One placement and one durability model

Choose publication **in the existing store pendingWrite continuation, exactly once after `await replaceFile(...)` resolves**. This explicitly supersedes the earlier first-postrename-continuation proposal. Do not modify renameOver or replaceFile, add a filesystem callback, directory fsync or retry, or route publisher failure through their retry/cleanup catches. Existing replaceFile flushes the temporary FILE then renames; it has no postrename directory sync. The feature claims process-level persistence/publication and process-restart recovery only, **not power-loss/directory durability**. An uncertain rename/IO outcome is unconfirmed, not an invented rollback.

The public commit linearization is one immutable tuple assignment after the definitive successful replaceFile return. During an overlapping pending write/read, a reader may see the previous **complete published cache tuple**, never mixed new values/old versions. It is not a disk-freshness receipt. All subsequent queued mutations stay behind the same pendingWrite and validate against the new committed state before acting. This allows a delay between physical rename and logical publication without claiming both occur in one filesystem operation. Once a post-primary publication failure is known, the previous tuple is explicitly degraded and is not served as valid/current for the changed disk bytes.

## Complete opted-in turn

State is private to the opted-in Annex store: (a) actual primary base and exact successful-primary receipt, (b) immutable public tuple or explicit unavailable state, and (c) staged candidate. Other stores retain their existing optimistic cachedSettings/displaySnapshot/rollback/updateLock behavior. The private actual base is never a pending Alias value.

1. Validate/clone a strict local patch at IPC entry; capture installed host, main document receipt where required, settings epoch, emergency and launch admission. Enqueue on the existing settingsWrites where appropriate, then on the existing pendingWrite; do not add another lock/queue. Check original admission at both turns.
2. At pendingWrite turn, take a detached clone of **actual primary base**, not a stale public tuple. Normal typed patches require a healthy versioned surface. Check epoch first, then every declared touched version; guard/grant/deadline checks are pure and current. Emergency internal mutations are separately permitted while the versioned surface is degraded and use actual primary base/receipt.
3. Invoke one synchronous pure mutation over the clone. No nested save/update, await, external callback, emit or IO. Reject undeclared editable changes, invalid touched keys, unauthorized metadata changes, overflows and schema failures before primary IO. Same-value LOCAL sets/unsets remain declared writes; MCP equal-value early return does not enter this turn.
4. Stage and freeze the complete candidate: stored values (including separately reviewed private witness), exact declared touched keys, public projected values, next revision and all field versions, original epoch and operation ownership receipt. Compute/allocate before primary replacement. Data only: no caller-supplied publisher/observer function, thenable, proxy, getter or authority callback in the publication plan. A private store-owned publisher performs a single reference assignment; TypeScript void alone is insufficient to promise synchronous behavior. Reject attempted async/throwing/reentrant callback registrations before IO.
5. Run existing recovery-copy behavior and `await replaceFile(file, serializedCandidate, mode, existingPrecondition)` **inside a pre-primary filesystem try/catch only**. Existing entry/prepare/check repetitions, Windows EPERM/EACCES/EBUSY retry delays, temp prefix/sweep/mode and cleanup remain unchanged. If it fails before any confirmed primary replacement, leave the public/actual base unchanged and return failure; if primary outcome is uncertain, mark the versioned surface unavailable and report unconfirmed pending controlled reread. Do not claim the absence of temp IO.
6. After successful return, mark the candidate as the **actual primary base/receipt** before any potentially failing publication. No await or user callback. This write is committed. A later failure cannot enter filesystem retry, temporary cleanup or legacy optimistic rollback. The exact private receipt retains staged versions even if public publication fails.
7. Outside that filesystem catch, publish the precomputed tuple exactly once by synchronous private reference assignment before resolving the turn, notifying, auditing or returning to wrapper callers. Reentrant public reads see one old/new complete tuple; no publisher-supplied callback runs between value/version assignment. `getSettings`/GET/opted-in peekLoaded read the published coherent state, not independently assigned caches.
8. If an injected unexpected publication fault occurs after confirmed primary replacement, mark public versioned currentness unavailable, preserve actual primary base/receipt and return **committed_unconfirmed with failure flag**, never refused/rolled-back. Refuse ordinary typed patches and suppress stale runtime/name activation. The older tuple may be retained only as clearly degraded display, never current DTO. Emergency stop/persistence remains usable and composes actual B plus network-off, not old public A. Do not silently reinitialize versions from equality.
9. On healthy publication, update opted-in loadedSnapshot/peekLoaded as committed-only using the existing shape and frozen/deep-cloned provenance; then return the actual committed before/after and owned version receipt. Runtime/name effects separately recheck original admission and ownership after awaits, before every start/stop/rebind/scan/status/activation/ACK. Audit/notification failure cannot turn an accepted disk write into a primary failure. Keep abort-before-notification order.

The full store/version/session implementations are missing in this docs freeze. In particular, no existing wrapper continuation is claimed to implement steps 6–8, and no publication callback has been installed. The generic seam may be implemented only after the full algorithm is reviewed, not merely because boundary signatures compile.

## Degradation recovery is an explicit privileged local state mutation

Propose `RELOAD_SETTINGS_SNAPSHOT` local IPC/preload/store action, shown only for degraded saved-settings state as “Reload saved settings.” It is **disk-read-only recovery**, not wholly read-only: it publishes local base/tuple/new random epoch. It takes a strict request identity/degradation identity; validates the registered main WebContents/main frame/exact entry URL/document incarnation and captures original runtime admission at entry. No remote/mobile/tool grant is created.

Healthy use returns not_degraded without IO/publication. GET/display reads never initialize, reread or heal. When degraded, the explicit action enqueues behind existing pendingWrite; it cannot release a stuck OS operation. Check sender/admission/degradation ownership at entry, queued turn, after read and immediately before publication. Strictly reread the actual primary with bounded plain-file/provenance checks: missing/unreadable/changed-during-read/invalid JSON/invalid settings or witness data stays degraded, with original bytes preserved. Do not use the legacy loader's default fallback, backup/migration writes, temp sweep or name-store initializer. Validate existing legacy settings in memory without truncating custom text or writing a migration. This is not an installation, restart or repair operation.

On valid source and still-current admission, stage and publish actual base plus one coherent tuple under a **new random settings epoch** with initial per-field versions0. No runtime enable/rebind, settings save, name-intent activation or equality-based adoption occurs. Show any saved/runtime-off discrepancy plainly; rereading enableServer:true does not start it. Old requests and owned receipts fail new-epoch checks. A lost sender, intervening emergency/purge/epoch change, or newer queued publication causes refusal/superseded status, not stale recovery publication; leave current actual state untouched. The emergency's immediate stop wins, and its later queued durable mutation uses the actual base.

The degraded state carries a main-created degradation id at the fault, not minted by GET. Main retains bounded invocation records (max32 per degradation, visible limit refusal without eviction/re-execution) keyed by requestId + degradationId + original main document. Duplicate pending calls join the same status/promise; completed duplicates return the recorded outcome without reread/epoch rotation. An unknown obsolete degradation id returns stale_degradation, never a new recovery. All requests still require current caller authority; a matching id is not permission. After a newer fault, prior ids cannot initiate another recovery. Stale result DTOs are filtered by renderer generation/request/load ordering; random epochs are not lexically ordered. No mutation is automatically retried after a lost reply.

If actual primary outcome was uncertain, validated controlled reread is the only in-process path to a new valid tuple; no inferred clock reset/defaults. If post-primary publication alone failed, actual private base/receipt remains known and emergency disk writes can still preserve it while public DTO stays degraded until explicit recovery. Recovery failure is typed and persistent; it never blocks immediate emergency stop.
