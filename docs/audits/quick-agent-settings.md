# Quick Agent settings audit

Source audit for the Agent settings usability change, 2026-11-19. No live agent settings, launches, restarts, grants, or provider setup were changed during this audit.

## Finding

The controls work for desktop quick runs with a selected parent. They are not obsolete, but “Defaults for quick agents [name] starts” implied broader coverage than the implementation provides. The page is now called **Quick agent defaults**, and its explanation identifies desktop parent selection, helper settings, and other launch paths.

Tool-list behavior remains provider/runtime dependent: the desktop path forwarding an allowed-tools list does not establish equivalent enforcement by every provider.

## Recommendations requiring product decisions

1. **Keep the functional values and saved custom text.** Place these controls under an expandable **Quick run defaults** area in Agent Settings, beside helper defaults, rather than treating “Quick agents” as a peer configuration/lifecycle page. The current patch clarifies the existing page without moving or deleting settings.
2. **Explain the three concepts at creation time.** Use “Agent” for a continuing named workspace, “Quick run” for a task run that may use a chosen parent's worktree/defaults, and “Helper” for a delegated durable agent governed by orchestration policy. Prefer one user-visible term per concept, while retaining internal IDs and compatibility fields. Coordinate this across desktop, phone, Actions and documentation before a broad rename.
3. **Define an explicit launch contract before consolidating code.** Recommend one resolver with options for which parent defaults apply, explicit override precedence, and an auditable effective launch summary. Align desktop/HTTP/WS quick runs after choosing the access fallback; preserve Actions' separately authorized unattended access and helper grants. Do not automatically make parent attribution inherit permissions, tools or templates.
4. **Show scope and effective values in the launch form.** When a parent is selected, show which defaults are inherited and which explicit/template values override them. A model selector displaying “Default” currently conceals that it may resolve to a parent's custom model.
5. **Review the running-parent lock separately.** The defaults controls are disabled while the parent runs, even though desktop launches read them for future quick runs. Consider allowing edits while the parent runs with copy saying they apply to newly started quick runs; prove launch-time reads and settings-save concurrency before changing this behavior.
6. **Track the remote discrepancies as behavior work.** HTTP omits the saved tools; WS omits parent-default resolution; access fallback differs. These are not reasons to silently remove settings. Add focused launch-contract tests and make a product decision about intended parity, including provider support, before implementation.

## Implemented usability scope

Shared page order is Settings → Skills → Instructions → MCP servers → remaining pages. Existing General settings remain available. Instruction builders use the available pane width; library addition sits below the block list in an expandable section. Inline, new/shared block dialogs, and the basic instruction-file editor share a Markdown draft preview while preserving source and save/discard/error behavior. Draft preview leaves wildcards as written and is labeled separately from the authoritative saved next-start/running-session preview. Each saved-preview block's name and text share one layout row; long names can increase that row's height, and narrow panes stack its label above its content. No JavaScript line-position measurement is required.
