## Result and recommendation

**The visible phone Dispatcher conversation does not use the desktop controller conversation reader.** A phone receives the chat agent identity; the controller route selects the separate work/coordinator agent. Changing the controller route cannot be justified as the phone refresh fix on this evidence.

**Demonstrated cost:** each ordinary phone chat GET loads/parses the whole selected session before filtering the Dispatcher view and choosing a bounded response page. Both awake and sleeping paths ultimately use the persisted normalized Clubhouse JSONL reader. Repeating GETs or requesting older pages repeats this work; a small response does not bound the input read. This proves an input-size-dependent host cost, not its magnitude or that it caused the reported live delay.

**Precise candidate, conditional on request/timing evidence:** give the phone snapshot acquisition path an incremental selected-session materialization, following the existing controller reader's cached-head/contiguous-tail/full-fallback pattern. Keep the complete session available for the existing pending/queue/control/visible-event fold and page builder. Scope it to acquisition in `handleMobileChatRoute`; do not change the controller contract, status route, native provider files or phone replay contract. A cache must have explicit bounded retention and invalidate on session/file replacement, sequence rollback, agent identity replacement, lifecycle reset and authorization/epoch transitions; cached data must never bypass final admission. This candidate reduces repeated disk reads/parsing, not necessarily full-session fold cost.

**No product fix is recommended for landing from this source-only triage.** Establish which requests the delayed phone actually makes and where time goes before choosing the candidate. In particular, do not replace the full session with `tail: limit`: hidden Dispatcher events, pending interactions, queue rows and older control/slash-command events make that behaviorally unsafe. Do not add `afterSeq` alone to the storage call: without `tail`, the current storage reader still reads/parses the full file before filtering.

## Actual reader and pagination

[ChatAgentRuntime.readTranscript](https://github.com/Agent-Clubhouse/Clubhouse/blob/c041e7082ca4f72eaf65d4d83c6902b44182fd08/src/main/services/agent-runtime/chat-runtime.ts#L1416) waits for its `emitChain`, then calls `readChatTranscript` with the runtime's current session ID. It does not query the provider's native transcript. Emission appends normalized events before publishing them. The phone's ordinary durable Dispatcher read does not use the separate passive bounded quick-agent branch (`tail: 2001`).

[Storage](https://github.com/Agent-Clubhouse/Clubhouse/blob/c041e7082ca4f72eaf65d4d83c6902b44182fd08/src/main/services/agent-runtime/chat-transcript.ts#L499) serializes reads, appends, migration and index saves per agent directory. The selected session is explicit or the index's most recently started/resumed session. With no `tail`, it calls `readText` (whole-file `fsp.readFile`), splits and parses JSONL, filters session, then optionally filters `afterSeq`. It does not read every historical session on each warm chat GET. With `tail`, it walks backward in 64 KiB blocks and then parses/slices; line count is not a hard byte cap.

The index is cached per process. [Cold load](https://github.com/Agent-Clubhouse/Clubhouse/blob/c041e7082ca4f72eaf65d4d83c6902b44182fd08/src/main/services/agent-runtime/chat-transcript.ts#L342) may migrate a legacy log, import its growth, repair changed session files and save the index. Warm `listChatSessions` maps/sorts cached summaries under the same serialization chain; it does not parse all session files every request. It can wait behind another read/append. Source supports possible waiting and cold-start work, not measured contention.

For phone pages, `current` is the full selected session; `phoneChatEvents` applies group-chat visibility only afterward. [Visibility rules](https://github.com/Agent-Clubhouse/Clubhouse/blob/c041e7082ca4f72eaf65d4d83c6902b44182fd08/src/shared/dispatcher-group-chat.ts#L101) omit tools/thoughts/plans/subagents and clean routed messages, retaining state events. Hidden events still incurred disk/parse work and participate in raw-session metadata/pending folds.

The phone handler accepts `sessionId`, `beforeSeq` and `limit` (default/max 2000); it implements no `afterSeq` delta selection. It filters visible events by `seq < beforeSeq` after the read. `lastSeq` describes raw selected-session events, not just visible events. [buildChatPage](https://github.com/Agent-Clubhouse/Clubhouse/blob/c041e7082ca4f72eaf65d4d83c6902b44182fd08/src/main/services/annex-chat-pages.ts#L233) reserves pending and queued state, walks newest eligible events backward, returns chronological events and `nextBeforeSeq`/`truncated`, and bounds encoded output to 8 MiB. Pending state is all-or-nothing with minimal forms or a 503; queued rows older than the page can be included. Output limits do not cap storage input.

The [controller reader](https://github.com/Agent-Clubhouse/Clubhouse/blob/c041e7082ca4f72eaf65d4d83c6902b44182fd08/src/main/services/annex-controller-chat.ts#L54) samples cached index head metadata, does one full initial read, then uses `afterSeq + tail` for changes, checks contiguous coverage and falls back to a full read on gaps. Unchanged head avoids transcript lines. Retention is at most two cached sessions with idle expiry checks of 120 seconds. It still holds full event arrays and folds/projections over history when producing pages; this is not proof of constant CPU or bounded bytes. Initial/history pages walk backward; `afterSeq` catch-up walks forward so bursts do not skip a page; limit defaults to 500/max 2000 and output max is 8 MiB. Peer budget starts at 20 reads, refills one/second, with 429 before transcript IO. These benefits are not present in the phone reader merely because the controller route exists.

## Subscription, incremental refresh and admission

- [Live delivery](https://github.com/Agent-Clubhouse/Clubhouse/blob/c041e7082ca4f72eaf65d4d83c6902b44182fd08/src/main/services/annex-server.ts#L6402): host subscribes once to normalized chat events, applies `phoneChatEvent`, strips remote-only content via `remoteChatEvent`, then bounds, buffers and broadcasts `chat:event`. No transcript GET is needed by that server path for each new event. There is no visible-chat-specific subscription command in this handler. Whether the phone unnecessarily refetches on these events is outside this source finding.
- [Replay](https://github.com/Agent-Clubhouse/Clubhouse/blob/c041e7082ca4f72eaf65d4d83c6902b44182fd08/src/main/services/annex-server.ts#L5666): `mobile:replay` requires matching mobile epoch and valid global transport sequence, verifies complete contiguous coverage and replayable frames, else sends `replay:gap`. Its sequence is distinct from each transcript's event `seq`. The ring retains up to 10,000 events, age one hour, and approximate 64 MiB byte budget; retention loss can require recovery, but no gap was observed here.
- [Snapshot refresh](https://github.com/Agent-Clubhouse/Clubhouse/blob/c041e7082ca4f72eaf65d4d83c6902b44182fd08/src/main/services/annex-server.ts#L7001): catalog/config snapshots coalesce into one host build, with pending refresh and race follow-up logic. Output events (`chat:event`, PTY data, omitted frames) do not themselves count as snapshot-state races. A new socket holds event frames until its initial snapshot baseline; failures/backoff can delay that baseline. This mechanism does not page or return the chat transcript, and is not proof of a live snapshot loop.
- [REST admission](https://github.com/Agent-Clubhouse/Clubhouse/blob/c041e7082ca4f72eaf65d4d83c6902b44182fd08/src/main/services/annex-server.ts#L5260): main-port endpoints require pinned paired-controller certificate authentication. [Authorizer](https://github.com/Agent-Clubhouse/Clubhouse/blob/c041e7082ca4f72eaf65d4d83c6902b44182fd08/src/main/services/annex-authorizer.ts#L91) checks pairing, role and pin; reverse transport additionally requires active desktop network membership and never grants phone access by direction alone.
- Phone chat captures epoch before IO, rechecks current authorization/epoch after reads and roots and before send, and checks admitted live runtime/session/native/display/registry identity to refuse changed reads (409). These gates can reject a completed read; they do not avoid the already-spent read cost. Desktop controller reader rechecks membership/grant/selected coordinator identity after IO; its response has no mobile epoch and is not a mobile replay baseline.
- Phone `/chat/sessions` and `/status` have initial route authentication but do not implement the chat handler's explicit post-await epoch/admission recheck. Do not claim all GET routes have identical epoch protection. This is a source distinction, not demonstrated exploitation or evidence explaining latency. A future cache must preserve the stronger chat checks.

## Acceptance still needed

No observed request counts, request ordering, response bytes, transcript sizes, host read/parse timings, phone rendering timings, replay gaps, authorization failures or installed-source attestation were collected. Therefore neither a controller polling explanation nor a status/session enumeration bottleneck nor a phone full-refresh loop is established. Existing controller tests describe unchanged-head avoidance, contiguous delta fallback, paging, rate limits and revocation; they were inspected, not executed. Candidate acceptance would require exact-head independent review plus proof that repeated phone snapshots avoid unchanged-file reads, preserve page/pending/queue/filter semantics, recover safely from discontinuity, and retain authorization/epoch/session gates. Live improvement remains separately unaccepted until measured on the actual delayed path.
