# Nov 27 mobile refresh: beta7 → beta8 host delta

Read-only, light static analysis by ReconnectHostDiff. Only this report was written. No workers, runtime probes, app reads/changes, test execution, benchmarks or restarts. Existing tests and prior diagnostic documents are source evidence, not newly passing checks. No live cause or fix is accepted by this report.

**Result:** beta8 adds two concrete full-snapshot triggers reachable by a paired phone, broader lifecycle/status data, and stricter phone chat read admission. Those deserve correlation first. It does **not** introduce the ordinary full-session phone transcript read, change the main-port WS ping/pong policy, or make the new desktop history/Details consumers execute for a phone. None of the changed paths establishes a persistent refresh loop or the reported multi-second delay.

## Reconnect snapshot churn: what changed and what did not

[First-snapshot admission and refresh coalescing](https://github.com/Agent-Clubhouse/Clubhouse/blob/30fd3ab0fdca6dbe75aed0b91e4c9878eded9b71/src/main/services/annex-server.ts#L7001) predate beta8 and have no delta in their implementation across these releases. A new socket holds replayable event frames until its baseline snapshot, and joins the host's single snapshot build. A broadcast refresh can serve existing sockets and first-snapshot waiters. The socket baseline cursor is taken per connection. Build failures, oversized snapshots, or real state changes during reads can cause retries/follow-ups; the raced follow-up delay remains 250 ms. `pty:data`, `chat:event`, and `frame:omitted` remain excluded from snapshot-state races. New permission/repo-key callbacks enter this existing mechanism; adding them is not evidence that coalescing itself regressed.

`grantSnapshotForPeer` changed in `cab7f5095`, but its new `pendingGrantRequests` projection requires an active desktop network member. Phones retain their prior self-device grant filtering. That desktop projection should not be counted as new phone snapshot payload. Conversely, rank 1's queue callback broadcasts to connected phones regardless of why the feature was introduced.

`d72569262` (#3740, Nov 19) classifies peer updates as `last-seen` versus topology and suppresses connection-sync feedback on last-seen-only notifications. This is a reduction of desktop federation churn, not a newly introduced phone snapshot loop. It does not prove that all host background cost disappeared. Physical mixed-version/endurance acceptance in its commit description was explicitly outstanding; this analysis ran no such checks.

## WS ping/pong

The [inbound server heartbeat](https://github.com/Agent-Clubhouse/Clubhouse/blob/30fd3ab0fdca6dbe75aed0b91e4c9878eded9b71/src/main/services/annex-server.ts#L6593) still runs every **30 s**, sets `wsAlive=false`, sends a WS control ping, and terminates a socket still false at a subsequent sweep. The connection listener marks it true initially and on WS `pong`. Application JSON traffic does not substitute for `pong`. Blame traces the sweep to `61ac97904` (March 29), and the release diff preserves it. There is no new JSON ping protocol or beta8 tightening of the missed-pong rule.

Beta8 adds `endUnauthorizedDetachedShells()` before the sweep (`d03180d93`), with a catch preserving the sweep if it throws. This is new synchronous work conditional on retained shells; it changes neither the heartbeat interval nor pong handling. Its runtime cost is unmeasured. Without detached shells it iterates an empty map. No evidence here supports attributing the incident to it.

The substantial [annex-client heartbeat change](https://github.com/Agent-Clubhouse/Clubhouse/blob/30fd3ab0fdca6dbe75aed0b91e4c9878eded9b71/src/main/services/annex-client.ts#L1717) in `6130b2966` (#3748) fences queued timers/timeouts to their captured outbound satellite socket so they cannot close a replacement connection. That runs on desktop → satellite connections. A phone connecting to this host's `/ws` uses the server path above. The host may run both connections, but outbound reconnect logs alone do not identify a phone disconnect. Reverse virtual subscribers answering ping by microtask are desktop control-lane machinery, also not the direct phone transport.

There is **no release diff** in `agent-runtime/chat-transcript.ts`, `annex-chat-pages.ts`, `annex-controller-chat.ts`, or `annex-event-replay.ts`. The ordinary runtime reader lineage predates beta7 (`cbf765b4e` / `fb74df7c7`); the changed line choosing an optional passive reader must not be mistaken for a new full-read implementation. Existing full-session/page details and safety caveats are in [host-path.md](host-path.md). Generic settings' catalog waits are covered separately in [settings-path.md](settings-path.md), not established as a new beta8 history cost here.

`a9d2c2558` (#3729, Nov 18) fixes desktop renderer remote-chat refresh revisions and reconnect PTY seeding. Its `chatStore.ts`/`AgentTerminal.tsx` behavior runs in the desktop UI, not the installed paired-phone UI. Likewise beta8's large reverse-control/receipt changes in `annex-client.ts` do not make phone REST use that outbound client. Exclude these as direct explanations unless independent phone-source evidence shows corresponding client code.

## Acceptance and next discriminator

The existing [incident summary](README.md) records similarly sized, zero-icon snapshots before both a slow and fast successful chat GET on beta8, and low sampled event-loop delay. That weakens an automatic attribution to snapshot encoding or icons; it does not establish snapshot counts, phone decoding time, or causation. This analysis adds no measurements and cannot supply a beta7 timing baseline.

For the next matched refresh, prioritize existing evidence of: (1) permission/repo-key changes and snapshot count around reconnect, (2) phone handling of the new snapshot/status/capability fields, (3) 409/403 responses and runtime identity changes, and (4) timestamps dividing catalog wait, chat dispatch, host handler, body transfer and visible render. A 2xx request spending seconds inside the host interval keeps the pre-existing full-session/emit-chain/storage path relevant even if the user first noticed it after an update. Preserve all authorization/session/epoch fences. No rollback or product change is justified solely by this static ranking.
