# Reset-aware Auto with provider reserves — proposal and isolated replay

Status: design only, task `t_mwojop1n`. Based on source commit `ae56577af786b0db79f21d137d0b334a5f7847dc`. No runtime policy, settings, UI, defaults, model mappings, telemetry destinations or live routing have changed. No provider starts, installs, PR, push, merge or release are part of this work.

## Recommendation and user experience

Offer an **opt-in preference for useful work before a plan resets**, with a provider-level retained reserve. Prefer a bounded 48-hour window, with stronger priority in the final 24 hours. Use observed whole-login pace to explain whether there appears to be budget that ordinary activity will leave unused. Retain the existing quality/difficulty mapping; never create jobs, probes, duplicate work, extra helpers, higher effort or longer answers merely to use quota. This changes the provider of an already authorized fresh Auto helper only. Existing work means real pending tasks suitable for a fresh helper, not moving or restarting an existing run.

Proposed settings copy in Smart selection:

| Control | Proposed initial choice when a person opts in | Meaning |
| --- | --- | --- |
| Prefer useful work before reset | On for that explicit opt-in | Prefer an eligible measured plan with usable budget in its final 48 hours; stronger preference inside 24 hours |
| Claude Code: Keep for me | 10% | Auto stops admitting against 90% of each applicable reported window |
| Codex: Keep for me | 10% | Independent percentage of this provider's own reported windows |
| Use more of the weekly plan in its final 24 hours | Off | Advanced, per provider: explicitly choose a smaller retained weekly reserve, e.g. 5%. Short/model windows retain their normal reserve |
| Allow Copilot as a last resort | Preserve the current saved switch | Quota unknown; reserve and reset controls unavailable until readable quota exists |

These are **recommendations for user consideration, not approved or changed defaults**. Existing installations with no new policy settings retain `weekly_used`, the current 80% ordering and 95% Auto admission threshold (5% reserve). Auto itself remains off unless enabled by existing scope rules. Existing `copilotAuto` defaults to true; preserve a person's explicit false, and show its actual value instead of silently treating this proposal as renewed consent. New UI should explain the unknown-capacity fallback visibly.

Example explanation: “Preferred Claude: its weekly plan resets in 18 hours, with 12 percentage points usable above your 10% reserve. Recent whole-login use is slower than that pace. The 5-hour window also passed.” With no rate history: “Preferred Claude: resets in 18 hours with usable budget. Recent pace is unknown.” Neither sentence promises completion or an exact quota saving.

The existing cycle score is `weeklyUsedBp - 10000 * (1 - hoursToReset / 168)`, plus a comparable qualified remaining mean when available. It is a linear cycle-phase preference, not a forecast of unused budget. It targets the full plan rather than a configurable usable allowance, affects the entire week and falls back globally if any measured reset is invalid. **A plan at 82%, resetting in 24 hours, still loses to one at 20%, resetting in six days, because low loses to headroom before scores are compared.** Merely enabling that score does not implement the request.

95% is Clubhouse's own Auto reserve, not a provider's hard limit. Preserve that distinction in code, copy and receipts. A measured percentage of 100% also must not be relabeled as provider-reported exhaustion.

## Budget, sustainable pace and evidence

All calculations refer to **one provider/login and one window**. For weekly fraction used `u`, retained fraction `r`, and hours to the provider-reported reset `T > 0`:

```text
remaining = 100% - u
usable budget U = max(0, remaining - r)
sustainable pace s = U / T                  [quota percentage points/hour]
observed pace b = positive quota delta / elapsed hours, same login/window/epoch
implied pace increase needed = s - b        [percentage points/hour]
projected unused usable budget D = max(0, U - b*T)
```

Example: 72% used, 10% reserve, reset in 24h gives `U=18 pp`, `s=0.75 pp/h`. A defensibly observed `b=0.25 pp/h` implies a `+0.50 pp/h` gap and a tentative 12 pp of unused usable budget. “Deficit” means rate increase needed to consume usable budget, not a quota shortage. Quota percentage points across plans do not imply equal tokens, money, requests or productive capacity. Cross-provider ordering is an explicit preference over each plan's own fraction and deadline, not an interchangeable resource calculation.

Rate evidence must be separate from stage 3's remaining-pressure prediction. Use only existing consented observations with arrival time strictly before the decision, same plan generation and reset epoch, increasing timestamps, no decrease/reset/plan transition, and fresh final evidence. Retain a bounded recent lookback and record coverage, elapsed time and uncertainty. The replay illustrates at least four samples spanning six hours within a 24-hour lookback, with the last sample at most 15 minutes old. **These are proposed evidence floors, not measured accuracy or qualified production thresholds.** Equal-time/delayed arrivals cannot train earlier decisions. Flat valid samples produce a reported zero; insufficient samples produce unknown.

Storage gap: [`recordQuotaSample`](../src/main/telemetry/helper-usage.ts) emits consented samples and remembers the last sampled quota in memory; [`helper-decision-ledger.ts`](../src/main/telemetry/helper-decision-ledger.ts) retains chosen decision/group evidence, not a general rate-series API for every candidate. Do not assume `forecastHistory()` supplies the required whole-login rate history, or parse telemetry files synchronously during routing. A later implementation needs a bounded event-fed buffer (proposed maximum 128 observations/provider, 24h retention) from the existing quota observations, with sample and arrival time, used bp, reset epoch and plan generation. Start process-local/cold after restart, clear on consent withdrawal or identity/reset transitions, and deduplicate reused cached samples. Add no polling or provider read solely to warm it. Persisting rate history later requires an explicit closed schema/retention review; calendar-only urgency works while history is absent.

Whole-login rate includes parent agents, terminal use, other applications and unattributed activity. Never divide it by helper count or label it a helper's consumption. An outside burst can suppress urgency once observed, but a burst that has not been read cannot be anticipated. Historical rate is neither future demand nor a counterfactual of what happens if routing changes. Do not extrapolate the stage 3 group delta to a rate, add overlapping whole-login estimates, or add `b*T` and a group prediction as if they were disjoint future consumption. Group bounds are used once for admission; rate is an urgency/diagnostic input.

Unknown rate is not zero: show calendar-only urgency with usable budget, without a numerical deficit. Missing/invalid/past/>7-day weekly reset disables that candidate's urgency and pace. Fresh readable usage without a reset still allows ordinary reserve-aware selection; a missing reset on one candidate does not disable another candidate's valid urgency. A passed reset never means silently set usage to zero: invalidate the old window and wait for a new read. No automatic extension to rolling windows without a documented provider deadline.

## Admission, urgency ordering and fallback

1. Preserve existing Auto permission/scopes, availability, cooldown, mapped quality/effort, mapping generation, start-lock and helper-cap checks.
2. Provider-reported hard limits and applicable short/model windows always constrain. A hard limit cannot be bypassed by urgency, user reserve relaxation or Copilot preference. An exhausted short window blocks a weekly plan even if the week resets soon.
3. Apply the configured Auto admission ceiling to each applicable measured window. Reject when observed used plus **one qualified aggregate upper bound beyond that sample** is at or above the ceiling. The group includes the proposed atomic start, live work and pending reservations exactly once; never sum per-helper whole-login residuals. Without qualified coverage use the observed reading, explicitly mark `forecast_unavailable`, and retain the current fallback rather than substituting a zero prediction. More conservative future admission would be a separate product choice, not an invented certainty from an uncalibrated model.
4. For an explicitly configured reserve, stale/failed/unknown usage or an unreadable applicable window cannot establish that it is respected: skip that measured provider until readable, complete evidence returns. Preserve old unknown fallback behavior for installations still on legacy policy. A missing weekly reset alone is not missing usage. A login reporting `not_applicable` has no enforceable reported subscription reserve; keep it outside reset/reserve ranking rather than label it unlimited.
5. For verified measured candidates passing admission, promote usable weekly budget with an apparent pace gap (or explicitly labeled calendar-only uncertainty): **0 < T <=24h first, then 24h < T <=48h**. Within a band, earliest reset wins; if resets tie, use the existing comparable-pressure comparison, lower load and rotation. This promotion precedes the old 80% tier, including temporarily unmeasured candidates, so urgency actually operates. Unverified mappings never gain urgency priority; valid existing fallback behavior remains available. No urgency if valid observed pace already meets/exceeds sustainable pace.
6. If nothing is urgent, retain headroom → temporary unmeasured where permitted → low ordering and current verified/pressure/load/rotation rules among admission-eligible candidates. The 80% boundary becomes a normal preference, not a hidden 20% reserve for urgent work. Unsupported-quota Copilot stays last behind **every eligible measured candidate**, including low ones.
7. Evaluate a separately configured final-24h **weekly** reserve first as part of admission; it is a standing explicit user choice, not a reaction to failure. No dynamic “nothing else available” relaxation. E.g. 92% weekly usage is excluded with keep-10%, admitted with explicitly configured keep-5%-in-final-24h if every other constraint passes; 95% remains excluded in that example. Short/model windows retain keep-10%. If no such option was configured, Copilot fallback or refusal wins over crossing the reserve.
8. When all measured providers are out, use Copilot only if its current allowance, mapping and operational checks pass. Record unknown usage / `last_resort_unmeasured`; never score it as zero, free or unlimited, invent a reset, or imply a reserve. With Copilot off/unavailable or no valid mapping, refuse with per-provider explanations and the earliest known reconsideration/reset time where available. Do not silently turn on Auto, cross the reserve, queue speculative starts or wait/spawn later without an independent task authorization. Existing no-cross-provider-retry behavior after failed spawn remains.

The replay explores only retain-10% and explicit retain-5% weekly relaxation. It does not qualify arbitrary reserve values, a zero reserve, or admission above today's 95% policy boundary. Product validation should decide the allowed range separately; the initial UI can offer 5/10/20% to avoid implying support for 100% consumption. This range is a proposal, not a provider hard limit.

**Reserve limitation: an admission threshold is not a physical remaining-balance guarantee.** In a deliberately tested cold-forecast burst, four useful 1%-of-plan starts all read 89%, all pass a 90% observed admission stop, and collectively finish at 93%. Outside activity or even a single unexpectedly large task can also cross the reserve. Qualified bounds reduce this risk and can refuse all those starts when their aggregate would reach 90%; they are empirically checked predictions, not a guaranteed ceiling. A stronger guarantee would require provider-enforced budgets, bounded task consumption or refusing all unbounded work; the current protocols do not provide it. Do not imply otherwise in the label “Keep for me”; explanatory copy must say “Auto stops choosing this provider at the threshold; running or outside work can still use more.”

## Why bounded urgency rather than raw deficit

| Alternative | Strength | Tradeoff / recommendation |
| --- | --- | --- |
| Existing cycle phase | Deterministic, easy to replay; same resets preserve weekly ordering | No rate/reserve semantics; old tiers defeat urgency; acts throughout week. Keep as comparator |
| Highest positive pace deficit `U/T-b` | Directly explains implied rate increase; responds to observed outside use | Sensitive to near-zero time, quantized/stale deltas, missing history and routing feedback; large distant budget can outrank an imminent reset. Do not make it sole cross-provider score |
| Bounded 24/48h urgency plus reserve admission | Directly expresses the requested 1–2-day useful-work preference; calendar-only fallback remains honest | Discrete edge changes, may concentrate work and increase another plan's admission gap. Prefer for explicit opt-in; pace is a conservative suppression/explanation signal, not an accuracy claim |

A focused example: A has 30% used and resets in 72h; B has 82% used and resets in 24h; each keeps 10%, and both valid historical rates are zero. Raw deficit picks A (`60/72 > 8/24 pp/h`), bounded urgency picks B. If B's observed whole-login rate is 1 pp/h, its urgency disappears. Boundary tests use one millisecond before/at/after 24 and 48 hours. Use the authoritative decision clock and immutable receipts. Hysteresis should be evaluated if real decisions flap; do not add a timer, dispatch loop or additional knob merely for this proposal.

## Scope, persistence and compatibility plan

The setting belongs to **the provider's shared local subscription**, across every Clubhouse orchestrator using that login, like the current app-wide mappings. A router is a consumer of that quota, not its own quota account. A project/agent can keep its existing Auto on/off authority; a repository cannot loosen a person's reserve. Do not offer independent per-router “10% buckets” that each assume the same remaining quota. If a future product needs a router-local stricter cap, combine it with the shared cap by taking the stricter admission ceiling and coordinate all reservations globally. Cross-device instances and outside applications remain outside the local start lock; say so explicitly.

Proposed future stored field: a versioned optional app-scope `autoBudgetPolicy` with a bounded mode enum and a map over supported provider ids containing retained percentage and optional final-24h weekly retained percentage. No expressions, scripts, task-content rules, per-model budgets or custom condition editor. Keep disabled provider values saved. Missing field means legacy behavior, not a migration to the new recommendations. Validate finite integer values/range; unknown schema/malformed present policy must disable affected new-policy starts and surface a settings error rather than silently reduce a saved reserve. Do not rewrite unrelated preset cells, cell generations, custom text or scope switches. Old-client read/write downgrade behavior needs explicit compatibility review because the current settings normalizer picks known keys and can drop a new field.

Extend `HelperRoutingSettings`/`HelperRoutingUpdate` with optional capability/versioned values, revision conflict handling and labels. Extend the current serialized settings writer, audit and changed notifications. Preserve sparse defaults for legacy absence, but persist a newly opted-in policy's selected reserves explicitly so a later default change cannot loosen them. Mapping Reset must not reset budgets or enable Copilot. A separate budget Reset should show exactly what it will restore before changing it.

Treat a higher retained reserve, removal of relaxation, narrower urgency allowance and fallback disable as restrictive writes. Stage them immediately, including when queued behind unrelated mapping/metadata saves; use the maximum retained reserve/minimum effective ceiling over committed and pending restrictions. Recheck at the start lock. Loosening waits for successful durable commit; failed writes release only their own pending restriction. A pending removal of relaxation must not be temporarily undone by a queued saved weaker policy. Do not advance mapping cell generations for a reserve-only change; do record the effective budget revision on a decision. App/project/agent Auto gates remain authoritative. Desktop/mobile/MCP partial updates must preserve fields not being edited, refuse stale revisions and reject project reserve loosening. Older phone clients should not gain write authority by omission; capability-gate the new controls while preserving existing preset-only contracts.

## Explanations and measurement plan

Add distinct policy-versioned reason/exclusion codes for reset urgency, observed reserve, predicted reserve, usage unavailable and explicitly configured relaxed reserve; keep `quota_exhausted` exclusively for provider evidence. The current `quota_near_limit` label says “close to its limit,” so it cannot adequately explain a user ceiling of 80/90%. Preserve generic old-code fallback for older clients. UI should show normal and currently effective reserve, which window blocked, checked-at time, reset-time basis and unknown forecast/rate independently. Do not present an old receipt as current quota.

Extend the existing **local-only consented** decision/candidate ledger with policy/config revision, configured/effective window ceilings, relaxation enabled/applied, time-to-weekly-reset, usable budget, supported forecast coverage and upper bound, rate evidence window/count/coverage, sustainable pace/deficit when known, urgency band, rank before/after promotion, fallback/refusal cause and missing-evidence reasons. Record a normalized schema, not raw rules, login names, prompts or task text. Bound receipt size and preserve retention/delete/export controls; no new destination or background sampler. Export any new fields only after a separate privacy review; raw rates/percentages/reset times remain local. Existing summary `reason`/policy version allow aggregate analysis without claiming helper attribution.

Simulation assumptions: A/B are abstract simulated subscriptions, each with arbitrary capacity 100 and 40 already used; A resets after 24h, B after 144h. Each requested useful task takes one hour and consumes 2.5 of that simulated provider's own units. One-hour ticks, serial arrivals, zero reading lag, whole-percent rounded readings, no failures/cancellations/outside use in the table, and no stage 3 model qualification or task-quality measurement. A final tick records A's reset; no tasks are requested after it. High demand requests 24 tasks, low demand four (every six hours), absent demand zero. Raw pace and non-relaxed research policies receive the same **assumed synthetic historical** whole-login rate of 25 bp/h; calendar-only relaxed policy has no rate estimate. The rate is illustrative, not fitted from these tasks and not live evidence. The synthetic common work unit is simulator truth, not a claim that real plans have equal capacity.

The committed results table and transcripts accompany this proposal under `docs/evidence/helper-reset-policy/`. Every policy receives identical arrival demand. High-demand assertions: weekly balance leaves 30% unused on A, existing cycle 20%, reserve-aware old tiers 20%, raw deficit and bounded urgency 10%, explicitly relaxed bounded urgency 5%. All 24 requested tasks are accepted in that fixture with no simulated depletion. This supports the tier-order observation and the behavior of the proposed priority; it does not establish measured quota savings, provider quality, lower cost or globally optimal scheduling. With absent demand no tasks are created and 60% expires unused under every policy. Low demand demonstrates that preference cannot manufacture useful work.

Focused checks also cover staggered resets, exact 24/48h edges, missing reset/usage, stale/future/partial evidence, short and model exhaustion, reserve equality and +/-1 bp, normal versus explicit relaxed reserves, aggregate upper-bound admission including concurrent/pending work, unqualified concurrent overshoot, observed outside activity represented as whole-login rate, changed plan/reset/decreasing/delayed rate evidence, unknown Copilot and opt-out/refusal. The simulator is not a replay of actual provider accounts; aggregate forecast qualification itself remains covered by existing stage 3 checks, not invented by this research module. A real overlapping-group/pending-settings/start-lock integration review remains deferred.

## User choices and phased implementation/review

Before any production work, the user still owns: whether to offer/enable this new policy; whether 48h/24h expresses the desired priority; which retained reserve each provider should use (10% is proposed); whether to allow any explicit final-24h relaxation (off proposed, 5% example); and whether the existing unknown Copilot fallback allowance remains wanted. Also confirm observation-only admission with honest overshoot disclosure versus a stricter cold-forecast behavior that can refuse useful tasks. No new choices are needed to finish this isolated design/replay assignment.

1. Review product semantics and evidence limits independently. Resolve the above choices, allowed reserve range, unknown-usage behavior, deadline ordering and acceptable concentration/admission gaps. No rollout approval is inferred from these replays.
2. In a separately authorized change, implement shared settings/types/normalization, atomic revisioned persistence, pending restriction handling and visible copy. Risk-targeted checks: failed queued restrictive saves, concurrent loosening, older clients preserving fields, unchanged mapping identities, explicit/preset/wake paths unaffected and project restrictions preserved.
3. Implement one pure selector plus full local receipts; integrate only under the existing start lock and permissions. Recheck short/model limits, expiry/staleness, group upper bound coverage, reservations once, Copilot allowance and live settings. Preserve quality mapping and no-retry constraints. Independent policy/concurrency/privacy review on the exact head before activation.
4. First evaluate on isolated chronological replay and, only if separately authorized, consented existing-work shadow decisions. Predeclare accepted/refused task non-regression, reserve crossings, fallback frequency, short-window depletion, unused **usable** fraction per window, time until useful work starts and maximum provider admission gaps. Do not optimize spread alone: intentional reset urgency increases it. Observe unknown coverage and forecast error, and stop promotion on invalid evidence. No live experiment or extra quota collection is authorized here.
5. A later explicitly approved opt-in release may activate the selected behavior. Keep one versioned legacy fallback, clear rollback and existing user settings intact. Landing, live routing and any default change each remain outside this assignment.
