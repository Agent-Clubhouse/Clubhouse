# Clubhouse-managed agents

Epic: #2819. Sub-issues: #2893 (New agent), #2894 (parts library), #2895 (builder), #2896 (delivery), #2897 (shared edits), #2898 (templates), #2899 (helpers), #2900 (MCP tools), #2901 (retirement), #2902 (built-in content).

## Model

- **Agent parts** are asset catalog entries of kind `block`, `skill` or `mcp` (`src/main/services/asset-catalog`). Built-in parts are installed by Clubhouse at startup and are read-only, and they follow the build that is running, older or newer (D100). Custom parts are the person's.
- **A managed agent** has `managed: ManagedAgentSetup` on its durable config: the ordered block ids, skill ids, MCP ids, and the template it came from. Its settings (CLI, model, effort, Free Agent Mode, orchestration, auto-sleep, helper template) are the ordinary agent settings, edited on its Settings page and carried by templates.
- **By reference.** A setup holds ids, so an edit to a part reaches every agent using it when that agent's next session starts.
- **Fork** makes a new custom part with the same content and records `forkedFrom`. Forking from an agent switches that agent to the copy. "Back to shared" switches it back.
- **Templates** are unlinked starting points. Built-in templates are data shipped with the app (`managed-agents/builtin-text/manifest.json`, read by `builtins.ts`). Custom templates live in `<app data>/managed-agents/state.json` with part descriptions and fork origins.
- **Built-in text** comes from the maintainer's builder. `node scripts/sync-builtin-text.mjs <export folder>` checks `managed-agents/builtin-text/` (block text, `manifest.json` and the generated `index.ts`) against an export, and `--write` updates it. Don't edit those files by hand. Cut built-ins are retired (D71): `retired` in the manifest. Since D99 a retired built-in is never installed, and at startup whatever uses one switches to a custom copy with the same name and text, visible and editable in the library; the built-in itself is removed.

## Delivery

`spawnAgentInner` (`agent-system.ts`) calls `deliverForSpawn` for a managed agent before the start, for both runtimes and every CLI:

- **Instructions:** the blocks are joined in order with a blank line between them, `@@AgentName`, `@@Path` and `@@StandbyBranch` are filled (any other `@@` token stays as written, D72), and the result is written with `provider.writeInstructions`. Clubhouse adds nothing else.
- **Skills:** each skill folder is written whole into `<worktree>/<configDir>/<skillsDir>/<skillName>`. A manifest file lists the folders Clubhouse wrote, so a later start removes only those. Any other untracked folder there is moved to app data, unless the skills folder is reached through a link or git can't say what it tracks (D48).
- **MCP:** JSON-format CLIs get their servers written to the worktree MCP file, and the Clubhouse bridge is injected into it afterwards. Every setup has the Clubhouse MCP part and every agent gets the bridge (D69). All CLIs get the same servers through `resolveProjectMcpServers` / `resolveAgentMcpServers`: launch flags in the terminal, SDK options in chat. Env is names only (D46).
- **Parent instruction files:** for Claude Code, CLAUDE.md files above the worktree go into `claudeMdExcludes` in the worktree's `.claude/settings.local.json`, and `.clubhouse-managed-excludes.json` records which entries Clubhouse added (D49). Preview lists what the CLI still reads besides the setup.
- An unmanaged agent gets nothing written into its folder at start: the Clubhouse Mode runtime was removed (D68). No agent has a persona layer in its orchestration policy since personas were retired (D67).
- An unmanaged agent that used Clubhouse Mode or a persona is switched to managed first (`managed-agents/auto-migrate.ts`, D59), so that start is already a managed one. A startup pass, once per app start, does the same for sleeping agents, and makes the source control setting that only followed from Clubhouse Mode explicit (D61). The MCP one (D63) went when the Clubhouse MCP became always on (D69).
- The wildcard helpers live in `agent-wildcards.ts`, the MCP server resolution in `agent-mcp-servers.ts`, and the TOML cleanup every TOML CLI start runs in `toml-config-cleanup.ts`.

The service remembers each running session's delivered fingerprint. `statusFor` compares it with the current setup to drive the "Setup changed" bar. `restartManagedAgent` stops the agent and resumes its last session, or starts a new conversation when asked or when the CLI changed.
