## Concrete path-isolation discriminator

No app/read was executed. The following is the source-derived baseline discriminator to reproduce in a bounded renderer test before correction:

1. Populate only `remoteProjectStore.remoteAgents` with a namespaced remote chat agent and remote project, as real snapshots do (`remoteProjectStore.ts:269–289`); leave the local agent/project stores empty. Wrap ChatStream/Markdown as AgentRuntimePane does using RemoteChatContext. Use an agent message containing `[report](/etc/passwd)` or a Windows absolute file path, plus a folder/file: link control. Never read those real files: mock all local APIs.
2. ChatStream sets media and file-chip contexts null for remote (`:355–357`, `:792`, `:830`), but still mounts RichLinkProvider (`:829`). The provider's local-only lookups produce projectId=null (`RichLinks.tsx:339–344`); repo resolution is normally skipped because dir is absent. Thus an automatic git.githubRepo(satellitePath) call is **not** observed from this normal store path today. An explicit identity guard is still needed before future metadata changes.
3. With rich enabled, openLink uses `!isRemoteProjectId(rich?.projectId || '')`, which becomes true for null (`RichLinks.tsx:230–234`). Because agentId is present, a path click invokes `chat.openLink(namespacedRemoteId, path)` on the controller. Main FILE_ACTION 'link' resolves through resolveChatLink/inspectChatLink locally (`chat-handlers.ts:277–290`); absolute files ignore the agent base. It returns a controller path for preview or calls shell.showItemInFolder for folders/unviewable files. A namespaced ID is not a guard here.
4. With rich disabled, RichLinkContext is null; Markdown's locality expression also sees null media/file contexts and empty project (`MessageBlocks.tsx:68`). `useSafeMarkdownLinks(true)` routes absolute links through openLocalFileLink to filePreviewStore; FilePreviewHost then invokes `window.clubhouse.file.preview(path)` (`:15`). Main IPC.FILE.PREVIEW resolves and reads the controller-local absolute path (`file-handlers.ts:45–55`). Its top-frame check cannot distinguish a remote transcript click from a local file request.
5. Existing `RichLinks.test.tsx:215` calls openLink directly with a fabricated remote projectId. That avoids the actual missing-local-metadata case; it does not prove the normal remote ChatStream path or flag-off path. Add a regression at the real context/store seam, with spies proving ZERO local file preview, chat file/stat/import, shell-action or git path calls, and a positive local control.

This is a user-click path, not proof of automatic remote-triggered file exfiltration. No live exploitation, local file read, network probe or UI input was performed. Main's readable-file policy is intentional (#2478); the defect is losing host provenance before that policy is invoked.

## Minimal coherent implementation proposal (not performed)

1. **Host provenance first.** Use explicit namespaced agent identity / RemoteChatContext in the common Markdown/link policy, independent of rich flag, current store presence and feature visibility. A remote absolute/relative/file:/drive path stays text/inert link; do not call controller-local chat/file/git/shell APIs. Guard repo discovery by host. Preserve normal http(s)/mailto behavior and local link previews. Never just remove existing comparisons or change tests to pass synthetic metadata.
2. **Typed bounded media and upload bridge.** Add narrowly typed Annex client/IPC/preload operations for `readChatMedia(machine, agentId, mediaRef)` and `uploadChatImage(machine, agentId, bytes)`, plus needed capability read. Reuse requestSatelliteRaw (pinned direct + existing reverse/bulk route selection, current lease/post-await auth). Do not expose generic URLs/queries/paths to renderer. Validate top app frame, agent/ref, Uint8Array and byte limits in main; validate response before publishing to renderer. Keep complete JSON/base64 response within `MOBILE_CONTENT_MAX_BASE64 + bounded metadata` and decoded <=8MiB. Copy fetched image through main clipboard; refuse remote reveal even if renderer invokes it. Use existing shared agent-address helpers if dispatching existing chat APIs by namespaced ID.
3. **Enable only image-by-reference rendering and image composer staging.** Separate local path permission from media visibility instead of removing `!remoteChat` wholesale. Route all stored-image thumbnails/full view/copy for remote through the bridge. Keep local Markdown imports, sent-image path fallback, file chips/audio/video file cards and path previews off for remote. For paste/drop/picker use File.arrayBuffer with upfront file-size check, remote image MIME/sniff constraints, no webUtils path, no local staging/temp. Feed uploaded IDs into the existing remoteChat.send and preserve failed/uncertain-send draft semantics. Use satellite `attachments.version` and runtime images capability; clear actionable errors for missing support/too-large/foreign/expired/revoked/disconnected/too-many/rate limit, no fallback protocol.
4. **No server protocol expansion expected.** Existing /content and /attachments satisfy the needed satellite contract. No new path-accepting route, auth/grant change, epoch rule, quota, WS clipboard behavior, body cap or provider driver change. Preserve original image name in the controller draft if useful; existing wire echo labels uploads phone-image and does not promise original-name fidelity. Changing that shared contract would be a separate small reviewed choice, not required for byte delivery.

Recommended acceptance boundary: stored remote image refs up to existing8MiB remote limit; pasted/dropped PNG/JPEG/GIF/WebP images up to existing3.75MiB each, ten per send; remote path isolation by omission. Generic file uploads, 20MiB remote media parity, remote file-chip/Markdown image resolution, original filename wire changes, video/audio/PDF transport and satellite GitHub repo resolution are not prerequisites for this finite image-focused contract. If the parent requires those, name the separate contract before implementing them.
