## Proven scope and limits

The new immutable B-tree-like index supports exact point lookup, bounded
pagination and copy-on-write roots with content hashes. Pages are at most
256KiB, nodes at most64 entries/references, detail LRU4 leaves (at most256
cached rows), reference-only LRU16 pages. Values/keys are validated before disk
publication. Old roots remain readable after update/delete; oversized later
values split by bytes, not only entry count. Invalid versions, reference
metadata and damaged bytes refuse without replacing the original file.

The1,024-row synthetic control exceeds64KiB of ID data. After a cold reopen,
point lookup uses at most4 disk reads; a200-entry page uses fewer than20. Cache
diagnostics remain within256 detail rows. These assertions cover this index
cache and API, **not total app heap**. Orphan pages create no manifest, current
generation or dispatch authority. Root activation still requires the separate
R1 transaction and failure/nonce controls, which are not implemented here.

The journal additionally releases volatile entered-ID tracking only after a
durable accepted commit; uncertain entered IDs survive callback-handle release.
The live repeated-success control demonstrates no entry-ID accumulation from
terminal accepted traffic. This does not allocate runtime generations.

Important remaining gap: existing sequenced journal/reducer still materializes
its sparse state. The lazy index is not wired into that authoritative state yet,
so the full hot-detail/archive contract is explicitly unresolved. Index GC,
installation marker/migration, post-ID/adoption, IPC/UI, shared runtime hooks,
wake, platform directory-flush behavior and full product-latency proof also
remain pending. No capability or remote field is advertised.
